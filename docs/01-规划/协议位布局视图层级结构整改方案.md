# 协议位布局视图层级结构整改方案

## 背景

协议编辑器需要展示帧协议文件中的字段定义。一个帧协议文件描述一次发送或接收数据的完整定义：发送时按照帧协议组包，接收时按照帧协议解析出业务关心的字段。

当前旧版 XML 帧协议通常使用 `ICDData` 根节点，主体内容在 `Data` 节点下。现有样例中存在两类结构：

1. `Data` 下直接定义多个 `Item`。
2. `Data` 下只有一个顶层 `Item`，该 `Item` 内部通过 `Childs` 定义子字段。

例如 `5V导光板电源_发送电流设定值_ComCHH50W_COM1.eprotox` 的结构是：

```text
Frame
├── byte0
├── byte1
├── byte2
├── byte3
├── 5V导光板电源 设定电流值
└── CRC校验
```

这些字段都是帧的直接组成部分。

而 `5272_00_自检_发送.eprotox` 的结构是：

```text
Frame
└── A429_IN1(001) 发送数据，dword，32bit
    ├── A429_IN1(001) Label，8bit
    ├── A429_IN1(001) SDI，2bit
    ├── A429_IN1(001) Data，19bit
    ├── A429_IN1(001) SSM，2bit
    └── A429_IN1(001) Parity，1bit
```

这里顶层 `Item` 表示一个完整的 32 bit 数据字段，`Childs` 表示该 32 bit 数据内部的位段定义。二者不是同级关系，而是“容器字段”和“内部子字段”的关系。

本方案的目标不是单纯美化 `IcdBitLayoutView`，而是让协议编辑器能准确表达现有 ICD 协议的领域结构：

```text
ICDConfig / Repository
└── Frame / ICDData
    └── Root Field / Item
        └── Child Field / Childs.Item
```

## temp/Schema 样本结构审查

### 配置文件：ICDConfig

`temp/Schema` 中存在大量 `ICDConfig` 文件，例如：

```xml
<ICDConfig>
  <Files>
    <FileInfo>
      <Name>5272_00_自检_发送</Name>
      <ID>4</ID>
      <Type>2</Type>
      <Description>5272_00_自检_发送</Description>
      <Enable>1</Enable>
      <WordType>0</WordType>
      <ByteOrder>0</ByteOrder>
      <Path>5272_00_自检_发送.xml</Path>
    </FileInfo>
  </Files>
</ICDConfig>
```

该结构表达的是：

```text
一个 ICD 配置 = 多个帧协议文件的集合。
每个 FileInfo 指向一个 ICDData 文件。
FileInfo 提供 frame id、frame type、byte order、enable 等元信息。
```

因此协议编辑器可视化不能只考虑单个 `.eprotox` 或单个 `ICDData` 文件，还要考虑：

```text
ICDConfig → 多个 Frame → 每个 Frame 的字段布局
```

### 普通串口/电源类帧：ICDData + 多个顶层 Item

普通串口、电源、示波器等协议文件通常是：

```xml
<ICDData>
  <Name/>
  <Data>
    <Item>byte0</Item>
    <Item>byte1</Item>
    <Item>业务数据字段</Item>
    <Item>CRC校验</Item>
  </Data>
</ICDData>
```

这类帧的领域含义是：

```text
Frame
├── 固定头 / 命令字节
├── 业务数据字段
└── 校验字段
```

这类可视化重点是：

1. 按字节顺序显示完整帧结构。
2. 区分固定值、业务字段、校验字段。
3. 展示默认值、枚举值、缩放、单位、绑定通道和字段语义。

例如字段常见属性包括：

```text
Name
Description
GroupName
SystemName
Unit
ValueTextList
ScaleA / ScaleB
ScaleFormula
ScaleConveror
LinkTo
Tag
IsScaled
Min / Max
```

### A429 类帧：ICDData + Childs

A429 类文件通常使用一个 32 bit 顶层字段表示完整 A429 word，再通过 `Childs` 描述其内部 bit field。

例如：

```text
Frame
└── ISI-01#A429_IN1(150) 发送数据，32bit
    ├── LABEL，8bit
    ├── SDI，2bit
    ├── UTC_SOURCE，1bit
    ├── UTC_Second，6bit
    ├── UTC_Minute，6bit
    ├── UTC_Hour，5bit
    ├── PAD，1bit
    ├── SSM，2bit
    └── PARITY，1bit
```

这类帧的可视化重点是：

1. 一个 32 bit A429 word 是完整顶层字段。
2. `Childs` 是该 word 内部的 bit field。
3. 必须显示 bit 段占位关系。
4. 不能把 parent 和 child 显示为同级字段。
5. 要能显示短字段，如 1 bit、2 bit、5 bit、6 bit 字段。
6. 字段宽度过窄时，需要 tooltip 或详情区补充完整名称、枚举和描述。

例如：

```text
0        7 8  9 10                 28 29 30 31
┌─────────┬────┬─────────────────────┬─────┬──┐
│ LABEL   │SDI │ DATA                │ SSM │P │
└─────────┴────┴─────────────────────┴─────┴──┘
```

### 样本质量问题

`temp/Schema` 中存在部分非干净 XML 样本，例如包含 Git 冲突标记：

```text
<<<<<<< HEAD
=======
>>>>>>> 65a49280ce73fa5643f132301f9d69071d289295
```

因此导入或打开 ICD 文件时，需要能识别并报告 XML parse error。UI 不应静默失败，也不应仅显示空白视图。

## icd_utility 基础设施支撑情况

### 已支持：ICDConfig 多文件加载

`Loader::init_with_metadata()` 已支持：

1. 解析 `ICDConfig`。
2. 遍历 `FileInfo`。
3. 根据 `Path` 加载每个 frame 文件。
4. 用 `FileInfo` 覆盖 frame 的 id、name、description、type、byte order。
5. 构建 `Repository`。
6. 返回 `LoadResult`。

`LoadResult` 中包含：

```cpp
Repository repository;
std::filesystem::path config_path;
Format format;
std::vector<FrameFileInfo> file_entries;
```

这说明基础设施已经能表达：

```text
一个协议配置包含多个帧协议文件。
```

### 已支持：ICDData 单帧解析

`parse_xml_frame()` 支持：

```xml
<ICDData>
  <Name/>
  <Data>
    <Item>...</Item>
  </Data>
</ICDData>
```

`parse_node()` 支持递归读取：

```xml
<Childs>
  <Item>...</Item>
</Childs>
```

因此普通帧和 A429 父子字段帧都能进入 schema 层。

### 已支持：schema 到 Repository 构建

`schema::build_repository()` 会递归构造：

```text
SchemaConfig
→ Repository
→ Frame
→ Node
→ children
```

`icd::Node` 已提供：

```cpp
const Node* parent() const noexcept;
icd::span<const std::unique_ptr<Node>> children() const noexcept;
void add_child(std::unique_ptr<Node> child);
void insert_child(std::size_t index, std::unique_ptr<Node> child);
bool remove_child(std::size_t index);
```

`icd::Frame` 已提供：

```cpp
icd::span<const std::unique_ptr<Node>> roots() const noexcept;
icd::span<Node* const> nodes() const noexcept;
const Node* find(std::string_view name) const noexcept;
```

所以底层模型已经具备父子结构基础。

### 已支持：.eproto / .eprotox 仓库格式

现有接口包括：

```cpp
deserialize_repository(...)
serialize_repository(...)
deserialize_xml_repository(...)
serialize_xml_repository(...)
```

`.eprotox` 的 `ICDProtocol` 格式支持：

```xml
<Children>
  <Item>...</Item>
</Children>
```

旧版 `ICDData` 兼容支持：

```xml
<Childs>
  <Item>...</Item>
</Childs>
```

### 已支持：旧版配置和帧文件写回

已有写回接口：

```cpp
serialize_xml_config(...)
serialize_xml_frame_file(...)
serialize_json_config(...)
serialize_json_frame_file(...)
```

旧版 XML 写回能输出：

```xml
<ICDConfig>...</ICDConfig>
<ICDData>...</ICDData>
<Childs>...</Childs>
```

因此基础设施不是只读，已经具备基础写回能力。

### 已支持：字段值 decode / set_value 的基础能力

`Frame::decode()` 会对 frame bytes 做解码。

`Node::decode()` 支持多种值类型：

```text
boolean
byte
word
shortint
smallint
longword
integer
ulong
float
double
bytes
string
```

`Node::set_value()` 也支持写回到 frame decode buffer，并会标记 child modified。

这为后续接收报文解析显示、发送报文组包编辑提供了基础。

## 基础设施缺口和风险

### 按名称查找节点不适合复杂 ICD

当前 `Frame::find(name)` 返回第一个匹配节点。

这对复杂 ICD 不够可靠，尤其是 A429 类结构中，未来可能出现不同 parent 下复用：

```text
LABEL
SDI
DATA
SSM
PARITY
PAD
```

位布局交互必须使用 node 指针或稳定 node id，不能继续依赖 name 作为唯一定位标识。

### 旧版 XML 类型映射存在运行时解析限制

旧版 XML 中常见：

```xml
<Type>int</Type>
<BitWidth>19</BitWidth>
```

或：

```xml
<Type>byte</Type>
<BitWidth>1</BitWidth>
```

这对结构展示没有问题，但当前 `Node::decode()` 对部分类型有固定宽度要求：

```text
ValueType::integer 需要 32 bit
ValueType::byte_ 需要 8 bit
```

因此：

```text
协议结构解析和可视化：基本支撑。
任意 bit 宽字段的运行时解析：尚不完整。
```

后续如果做报文解析或组包，需要补齐：

```text
可变 bit width unsigned integer 解码。
可变 bit width signed integer 解码。
可变 bit width enum / flag 解码。
set_value 对 bit field 的写入。
```

### node-level 大端语义尚未完整进入 decode

样本中存在类似描述：

```text
仅此项是大端
```

现有 `Tag` 中有：

```cpp
Tag::big_endian_value
```

旧 XML tag 映射中也支持：

```text
Tag 60 → big_endian_value
```

但当前 `Node::decode()` 主要接收 frame-level byte order：

```cpp
Node::decode(frame_bytes, frame_order)
```

未看到根据 node tag 覆盖 byte order 的完整逻辑。

因此可视化应先标出“该字段是大端字段”，运行时解析阶段再补齐 node-level endian override。

### ICDConfig.xsd 只定义配置，不定义完整 ICDData

`temp/Schema/IcdConfig.xsd` 只定义：

```text
ICDConfig
Files
FileInfo
```

没有定义：

```text
ICDData
Data
Item
Childs
```

因此不能把 XSD 视为完整帧协议约束。当前 `ICDData` 支撑主要来自代码 parser。

### 写回不一定完全保真

旧版 `FileInfo` 中包含：

```xml
<Enable>
<WordType>
```

当前基础设施主要保留核心字段：

```text
Name
Path
ID
Description
Type
ByteOrder
```

如果目标是“编辑后完全保真写回原始 ICDConfig”，还需要补充元数据保留能力。

如果目标是“加载、展示、编辑核心帧字段并写出可用配置”，现有基础设施基本够用。

## 当前 IcdBitLayoutView 的问题

当前 `IcdBitLayoutView::loadFromFrame()` 会遍历 `frame.roots()`，再通过 `collectAllNodes()` 将 root node 和所有 child node 递归收集到同一个列表。随后按 `offset`、`start_bit`、`bit_width` 排序，并对每个 node 调用 `addBlock()` 绘制为独立区块。

因此，类似 `5272_00_自检_发送.eprotox` 的帧在位布局视图中会被显示成多个同级块：

```text
A429_IN1(001) 发送数据
A429_IN1(001) Label
A429_IN1(001) SDI
A429_IN1(001) Data
A429_IN1(001) SSM
A429_IN1(001) Parity
```

这种显示方式的问题是：

1. 父子关系丢失。
2. 容器字段和内部子字段被误表达为同级字段。
3. Frame 作为一次完整收发数据定义的语义没有被体现。
4. 按 name 查找 node 存在定位错误风险。
5. 无法准确表达 A429 这类 32 bit word 内部 bit field 结构。

## 可视化要求清单

整改后的协议可视化应覆盖以下层次。

### 配置级可视化

面向 `ICDConfig` / `Repository`：

1. 显示当前配置包含哪些帧。
2. 显示每个帧的：
   - ID
   - Name
   - Type
   - ByteOrder
   - Path
   - Description
   - Enable（基础设施后续补齐）
3. 支持从帧列表切换到具体帧布局。
4. 加载失败时显示文件路径和 parse error。

### 帧级可视化

面向 `ICDData` / `Frame`：

1. 将一个 frame 作为一次完整发送或接收数据定义展示。
2. 显示 frame length。
3. 显示 frame type 和 byte order。
4. 显示 root fields 的整体顺序和占位。
5. 区分普通帧和 A429 容器字段帧。

### 字段级可视化

面向 root `Item` / `Node`：

1. 显示字段名称。
2. 显示 offset、start bit、bit width。
3. 显示 value type。
4. 显示字段是否有 children。
5. 显示 Tag 语义，例如固定值、业务信号、校验、大端字段。
6. 显示单位、缩放、枚举和 LinkTo。

### 子字段级可视化

面向 `Childs.Item`：

1. 显示 child 在 parent 内部的 bit range。
2. 用 parent 容器表达 child 归属关系。
3. 支持 1 bit、2 bit 等窄字段。
4. 支持 hover / click / context menu / highlight。
5. 字段过窄时使用缩写、tooltip 或详情区展示完整信息。

### 语义级可视化

字段不只是 bit range，还包括业务语义。

建议在 badge、tooltip、属性面板或详情区中表达：

```text
Tag
ValueTextList
Unit
ScaleA / ScaleB
ScaleFormula
ScaleConveror
Min / Max
LinkTo
SystemName
GroupName
IsScaled
```

尤其是：

1. `ValueTextList`：枚举、默认值或固定值。
2. `Unit`：工程单位。
3. `ScaleA` / `ScaleB`：线性缩放。
4. `LinkTo`：绑定通道。
5. `Tag 40`：固定值、校验或特殊控制字段，需要结合上下文显示。
6. `Tag 41`：业务信号值字段。
7. `Tag 60`：大端字段。

## 推荐设计：面向 ICDConfig / ICDData 的 Frame 层级位布局视图

推荐将 `IcdBitLayoutView` 从“字段列表视图”调整为“Frame 层级位布局视图”。核心不是在现有扁平区块上简单增加缩进，而是重建位布局视图的显示模型、交互标识和 bit 坐标规则。

### 设计原则

1. **Frame 是完整展示对象**
   - 一次发送或接收数据必须作为整体展示。

2. **Root Item 是帧的直接组成部分**
   - 不应被 child 打散为同级字段。

3. **带 Childs 的 Item 是容器字段**
   - parent 表示完整数据字。
   - child 表示内部 bit field。

4. **bit_width 是真实占位依据**
   - 旧 XML 中 `Type=byte` 但 `BitWidth=1` 时，可视化应按 1 bit 画。
   - `Type` 是值解释提示，不是占位宽度来源。

5. **交互必须基于 node 指针**
   - 不再使用 name 作为唯一定位依据。

6. **结构展示和运行时解析分层推进**
   - 第一阶段先准确展示 ICD 结构。
   - 后续再补齐可变 bit width decode、node-level endian 等运行时能力。

### 总体结构

新的位布局结构建议如下：

```text
IcdBitLayoutView
└── IcdBitLayoutScene
    ├── FieldSectionItem
    └── ContainerFieldItem
        ├── Parent field header / outer frame
        └── ChildFieldItem...
```

职责划分如下：

```text
FieldSectionItem
```

负责没有 children 的普通 root node。

```text
ContainerFieldItem
```

负责有 children 的 root node。它表达父字段的整体范围，并承载内部子字段。

```text
ChildFieldItem
```

负责容器字段内部的子字段，支持点击、hover、右键菜单、高亮和 tooltip。

建议再抽象一个共同基类：

```cpp
class LayoutNodeItem : public QGraphicsObject {
 public:
  virtual const icd::Node* node() const = 0;
  virtual void setHighlightedNode(const icd::Node* node) = 0;
  virtual int totalHeight() const = 0;
  virtual int sectionWidth() const = 0;
};
```

然后：

```cpp
class FieldSectionItem : public LayoutNodeItem;
class ContainerFieldItem : public LayoutNodeItem;
```

`IcdBitLayoutScene` 不再只保存 `QVector<FieldSectionItem*>`，而是保存：

```cpp
QVector<LayoutNodeItem*> items_;
```

这样 scene 只负责排列、清理、高亮和信号转发，不需要关心具体是普通字段还是容器字段。

### 数据处理规则

`IcdBitLayoutView::loadFromFrame()` 不再递归拍平所有节点。

新的处理流程：

1. 清空 scene。
2. 遍历 `frame.roots()`。
3. 对每个 root node 判断是否有 children。
4. 没有 children 的 root node：
   - 创建 `FieldSectionItem`。
5. 有 children 的 root node：
   - 创建 `ContainerFieldItem`。
   - 将 root node 作为容器父字段。
   - 将 children 创建为容器内部 `ChildFieldItem`。
6. 以 root node 顺序或 root node 的绝对 bit 起点作为顶层排序依据。
7. 计算 scene rect 并重置视图位置。

顶层不再显示“parent 和 children 同级排列”的结果。

### bit 坐标规则

必须以 frame 内绝对 bit 坐标作为唯一权威。

计算规则：

```text
absolute_start = offset * 8 + bit_offset
absolute_end = absolute_start + bit_width - 1
```

对于普通 root node，直接按自身 bit width 绘制。

对于 container root node：

```text
parent_start = parent.offset * 8 + parent.bit_offset
parent_end = parent_start + parent.bit_width - 1
```

每个 child：

```text
child_start = child.offset * 8 + child.bit_offset
child_end = child_start + child.bit_width - 1
relative_start = child_start - parent_start
relative_end = child_end - parent_start
```

如果：

```text
relative_start < 0
relative_end >= parent.bit_width
```

则说明 child 超出 parent 范围，UI 应标记为异常，而不是静默绘制成正常字段。

### 交互标识规则

当前接口：

```cpp
void blockClicked(const QString& name);
void contextMenuAction(const QString& name, const QString& action);
void blockHovered(const QString& name, bool on);
void highlightBlock(const QString& name);
```

建议替换为：

```cpp
void nodeClicked(const icd::Node* node);
void nodeContextMenuAction(const icd::Node* node, const QString& action);
void nodeHovered(const icd::Node* node, bool on);
void highlightNode(const icd::Node* node);
```

`ProtocolEditorWidget` 中的联动逻辑改为直接使用 node 指针：

```cpp
connect(bit_view_, &IcdBitLayoutView::nodeClicked, this,
        [this](const icd::Node* node) {
          if (!node) {
            return;
          }
          auto* editable_node = const_cast<icd::Node*>(node);
          bit_view_->highlightNode(node);
          property_panel_->showNode(*editable_node);
          node_tree_->selectNode(node);
        });
```

这样可以避免同名节点定位错误，也能准确区分 parent node 和 child node。

### 高亮规则

`ContainerFieldItem::setHighlightedNode()` 应支持两种情况：

1. 高亮 parent node：
   - 容器外框和标题高亮。
2. 高亮 child node：
   - 容器保持轻量关联状态。
   - 对应 child 位段高亮。

### 刷新和联动规则

需要保证树、位布局、属性面板三者状态一致。

#### 树选中节点

```text
IcdNodeTreeWidget::nodeSelected
→ IcdBitLayoutView::highlightNode(node)
→ IcdPropertyPanel::showNode(node)
```

#### 位布局点击节点

```text
IcdBitLayoutView::nodeClicked
→ IcdBitLayoutView::highlightNode(node)
→ IcdNodeTreeWidget::selectNode(node)
→ IcdPropertyPanel::showNode(node)
```

#### 位布局 hover 节点

```text
IcdBitLayoutView::nodeHovered
→ IcdNodeTreeWidget::revealNode(node)
```

#### 属性面板修改节点

当前属性面板修改 node 后只刷新位布局。整改后建议同步刷新树：

```text
IcdPropertyPanel::nodeModified
→ setModified(true)
→ refresh current frame layout
→ refresh or update node tree
→ restore current node selection if pointer 仍有效
```

### 语义显示设计

位布局视图不应该只画 bit cell，还要承载 ICD 字段的业务语义。

建议分三层展示：

1. **区块主显示**
   - name
   - bit range
   - value type
   - bit width

2. **badge / icon**
   - fixed value
   - signal value
   - checksum
   - big endian
   - scaled
   - enum
   - linked channel

3. **tooltip / 属性面板详情**
   - description
   - ValueTextList
   - Unit
   - ScaleA / ScaleB
   - ScaleFormula / ScaleConveror
   - Min / Max
   - LinkTo
   - SystemName
   - GroupName

其中窄字段，如 1 bit、2 bit 字段，在主显示中可使用缩写，在 tooltip 中显示完整信息。

### 异常数据规则

需要明确以下异常情况的处理方式：

1. **child 超出 parent 范围**
   - 标记为越界。
   - 仍允许点击并显示属性。
   - tooltip 中提示实际范围和 parent 范围。

2. **child 之间 bit range 重叠**
   - 标记冲突区域。
   - 不阻止显示。
   - tooltip 中提示与哪些 child 重叠。

3. **children 未覆盖完整 parent**
   - 正常允许。
   - 空白区域显示为未定义位段。

4. **XML parse error**
   - 显示错误文件路径。
   - 显示 parser 返回的错误信息。
   - 不静默显示空白视图。

5. **多层 children**
   - 第一版支持 parent + children 两层主视图。
   - 更深层 children 可先在 child tooltip 或局部展开区域中展示。
   - 后续如果多层结构成为常态，再将 `ContainerFieldItem` 递归化。

## 不再推荐的方案

之前提到的“缩进式分组显示”和“模式切换显示”不再作为推荐路径。

### 缩进式分组显示

该方案可以表达树形关系，但不能完整表达 bit 占位关系。它更像节点树的另一种展示形式，不适合作为位布局视图的核心整改方向。

### 模式切换显示

该方案通过“顶层字段”和“展开子字段”两个模式避免混淆，但会引入额外视图状态。用户需要理解当前模式，且 parent 与 child 的同一段数据关系仍不如容器内部位段直观。

这两个方案可以作为后续辅助能力，但不适合作为当前主方案。

## 分阶段落地路径

### 第一阶段：结构可视化

目标是准确表达现有 ICD 结构。

工作内容：

1. 引入 `LayoutNodeItem` 抽象基类。
2. 将 `FieldSectionItem` 改为持有 `const icd::Node*`。
3. 将 `IcdBitLayoutView` 信号改为 node-pointer-based。
4. 将 `highlightBlock(QString)` 改为 `highlightNode(const icd::Node*)`。
5. 将 `IcdBitLayoutScene` 的 `QVector<FieldSectionItem*>` 改为 `QVector<LayoutNodeItem*>`。
6. 修改 `ProtocolEditorWidget` 的位布局联动逻辑，取消 `current_frame_->find(name)`。
7. `loadFromFrame()` 改为以 `frame.roots()` 为入口构建顶层布局项。
8. 新增 `ContainerFieldItem` 和 `ChildFieldItem`。
9. 有 children 的 root node 显示为容器字段。
10. children 按 parent 内部 bit range 显示。
11. 保持普通多 root 字段帧显示不退化。

### 第二阶段：字段语义可视化

目标是让位布局视图表达 ICD 字段的业务含义。

工作内容：

1. 显示 Tag 语义。
2. 显示 ValueTextList。
3. 显示 Unit。
4. 显示 ScaleA / ScaleB / ScaleFormula / ScaleConveror。
5. 显示 LinkTo。
6. 显示 node-level big endian 标记。
7. 为窄字段增加 tooltip 或详情展示。
8. 增加 parse error 友好提示。

### 第三阶段：运行时解析和组包能力补齐

目标是支撑接收解析和发送组包。

工作内容：

1. 支持可变 bit width unsigned integer decode。
2. 支持可变 bit width signed integer decode。
3. 支持 enum / flag 类 bit field decode。
4. 支持 node-level endian override。
5. 支持 bit field `set_value()`。
6. 增加报文预览和字段值编辑能力。

### 第四阶段：配置写回保真

目标是让 ICDConfig / ICDData 编辑后尽量保留原始工程配置语义。

工作内容：

1. 保留 `Enable`。
2. 保留 `WordType`。
3. 保留原始 `FileInfo` 中未参与模型构建的元数据。
4. 保持 frame file path 稳定。
5. 写回旧版 XML 时尽量保留业务可用结构。

## 测试策略

行为变化需要先补测试，再实现。

建议新增或调整以下测试：

1. **无 children 的 frame 保持普通字段显示**
   - 构造多个 root node。
   - 调用 `loadFromFrame()`。
   - 验证 scene 中生成多个普通字段项。

2. **有 children 的 root node 显示为容器字段**
   - 构造一个 32 bit parent，包含多个 child。
   - 调用 `loadFromFrame()`。
   - 验证顶层只有一个容器字段，而不是 parent + children 的同级列表。

3. **child 相对 bit range 计算正确**
   - parent: 0..31。
   - children: 0..7、8..9、10..28、29..30、31。
   - 验证转换后的相对范围正确。

4. **child 点击发出准确 node 指针**
   - 构造同名 child 节点。
   - 模拟点击第二个 child。
   - 验证收到的是第二个 child 指针，而不是 `Frame::find(name)` 的第一个匹配项。

5. **树选中 child 后位布局能高亮 child**
   - 调用 `highlightNode(child)`。
   - 验证容器内对应 child 处于高亮状态。

6. **异常 child 被识别**
   - 构造 child 超出 parent 范围。
   - 验证 item 标记为异常状态。

7. **旧版 XML 样本解析测试**
   - 覆盖普通多 root 帧。
   - 覆盖 A429 `Childs` 帧。
   - 覆盖 parse error 样本。

8. **运行时解析补齐测试**
   - 覆盖 1 bit、2 bit、5 bit、6 bit、19 bit 字段 decode。
   - 覆盖 node-level big endian 字段。
   - 覆盖 bit field set_value。

## 验收标准

完成后应满足：

1. 打开普通电源/串口类 ICDData：
   - 位布局视图显示多个顶层字段。
   - 按字节和 bit 顺序表达完整帧结构。
   - 固定值、业务字段、校验字段有可识别语义。

2. 打开 A429 类 ICDData：
   - 位布局视图不再把 parent 和 children 显示为同级字段。
   - 32 bit A429 word 显示为容器字段。
   - `LABEL`、`SDI`、`DATA`、`SSM`、`PARITY` 等显示为容器内部 bit field。

3. 点击任意子字段：
   - 属性面板显示该子字段信息。
   - 左侧节点树定位到该子字段。
   - 即使存在同名节点，也定位到实际点击的 node。

4. 点击父字段：
   - 属性面板显示父字段信息。
   - 左侧节点树定位到父字段。

5. 修改字段名称、offset、start bit、bit width 后：
   - 位布局刷新。
   - 节点树刷新或保持一致。
   - 当前选择状态尽量保留。

6. 打开 ICDConfig：
   - 能看到配置内多个 frame。
   - 能切换 frame 并查看对应位布局。
   - frame 的 ID、Type、ByteOrder、Path 等元信息能被展示。

7. 异常结构能被识别：
   - child 超出 parent 范围。
   - child 之间范围重叠。
   - parent 未被 children 完全覆盖。
   - XML parse error。

8. 新增或调整的测试通过。

## 结论

`src/icd_utility` 已经基本支撑现有 ICD 协议的结构解析、父子字段建模、仓库序列化/反序列化、旧版配置和帧文件写回，也提供了运行时 decode / set_value 的基础能力。

但当前 `IcdBitLayoutView` 仍然停留在“递归拍平字段列表”的显示模型，不能精准表达现有 ICD 协议中的：

```text
ICDConfig 多帧集合
Frame 完整收发数据
Root Item 顶层字段
Childs 内部 bit field
Tag / ValueTextList / Scale / Unit / LinkTo 等业务语义
```

推荐整改方向是“面向 ICDConfig / ICDData 的 Frame 层级位布局视图”。该方案以 `frame.roots()` 为顶层入口，以 node 指针作为交互标识，以 frame 内绝对 bit 坐标作为占位权威，用容器字段表达 `Childs` 结构，并逐步补齐字段语义显示、运行时解析和配置写回保真能力。

缩进式分组和模式切换只能局部缓解父子关系展示问题，不能精准表达 bit 占位和帧协议组包/解析语义，因此不作为主路径。
