# 测试执行业务流程

> **日期**: 2026-07-28
> **状态**: 业务流程梳理
> **用途**: 记录 IDE 的完整使用流程与关键设计约束，作为后续方案设计的背景参考

## 1. 两种运行模式及其物理约束

ETest 平台的用户是测试工程师，使用真实或 Mock 的测试设备组合对被测对象（UUT）进行自动化测试。运行模式由物理链路的连通性决定，只有两种：

### 1.1 真实模式

| 组成 | 状态 |
|---|---|
| 硬件插件 | 全部真实驱动 |
| 物理连线 | 真实线缆 |
| UUT | 真实被测设备 |

信号经真实插件发出 -> 真实线缆 -> 真实 UUT -> 真实回复 -> 真实插件接收，形成物理闭环。

### 1.2 Mock 模式

| 组成 | 状态 |
|---|---|
| 硬件插件 | 全部 Mock 插件（`openDevice()` 是 no-op，读写纯内存） |
| 物理连线 | 不需要 |
| UUT | MockUUT（软件模拟被测单元的收发行为） |

数据流全程在内存中流转，零物理 I/O，纯软件闭环：

```
StepRunner.writeFrame
  -> Mock 插件.writeData（内存写入）
  -> MockUUT.onFrameWritten（查配置，返回回复字节）
  -> Mock 插件.writeData（回复写入内存）
StepRunner.read
  -> Mock 插件.readData（内存读出）
```

### 1.3 物理约束：模式是全局二值的

**混合模式物理上不通**：Mock 设备写的数据到不了真实设备，真实设备的信号进不了 Mock 设备。拓扑中 UUT 端口跨接两种设备时，信号链路必然断裂，测试结果不可预期。

因此模式选择是**全局二值**的，不存在逐设备选择：

- 全部 Mock 插件 -> Mock 模式
- 全部真实插件 -> 真实模式
- 混合 -> 不合理，应拒绝运行

## 2. 完整使用流程

### 2.1 编辑模式（page0）

```
① 创建测试工程
② 编辑 ICD 协议（帧结构、字段、编解码规则）
③ 编辑拓扑（UUT + 设备 + 连线 + 端口绑协议帧）
④ 创建测试程序（选信号、写步骤）
```

page0 的产物是**与模式无关的静态资产**：拓扑文件、ICD 协议、测试程序。这些资产在真实模式和 Mock 模式下完全一样。

### 2.2 运行模式（page1）

```
⑤ 设置运行配置（程序选择、通道选择...）
⑥ 运行（单程序 / 运行全部）
⑦ 查看结果（步骤 PASS/FAIL、监听器数据）
⑧ 生成测试报告（待实现）
```

page1 决定「怎么跑」-- 用哪个测试程序、监听哪些通道、结果如何呈现。

## 3. 产物与依赖关系

### 3.1 三大产物的编辑顺序

编辑顺序不强制，可灵活穿插，但存在数据依赖：

| 产物 | 内容 | 编辑时是否需要其他产物 |
|---|---|---|
| ICD 协议 | 帧结构、字段、编解码规则 | 独立，不依赖拓扑或测试程序 |
| 拓扑 | UUT、设备、连线、端口绑帧 | 绑协议帧时需要 ICD（否则只能手填帧名） |
| 测试程序 | 测试步骤、信号引用 | 选信号时需要拓扑 + ICD |

典型工作流：先画拓扑结构 -> 编辑 ICD 协议 -> 回来绑协议帧 -> 创建测试程序。或先编协议再画拓扑。

### 3.2 运行时依赖

运行时三者必须全部就绪：

```
拓扑（.etopo）
  ├─ devices[]          -> 设备列表 + pluginId + 端口
  ├─ products[]         -> UUT 列表 + 端口 + sendFrames/receiveFrames
  └─ connections[]      -> UUT 端口 <-> 设备端口 的连接关系

ICD 协议（.eprotox）
  └─ 帧定义             -> 帧名 -> frameId 映射 + 帧内字段结构

测试程序（.tcase）
  └─ 步骤列表           -> 每步操作一个信号（UUID 标识）
```

信号 UUID 的核心字段来源：

| UUID 字段 | 来源 |
|---|---|
| deviceId | 拓扑中的设备定义 |
| frameId | 拓扑端口绑定的帧名 -> ICD 查 frameId |
| 信号路径 | ICD 帧结构中的字段定义 |

### 3.3 协议与模式无关

ICD 协议在真实模式和 Mock 模式下**完全一样** -- 帧结构、编解码规则不因模式而异。模式只影响硬件层（用真实插件还是 Mock 插件），不影响协议层。

## 4. 模式的确定方式

### 4.1 由拓扑选用的插件类型决定

模式不需要运行时开关切换，**在拓扑编辑时就已确定**：用户选择设备时选用的 pluginId 隐含了 mock/真实信息。

每个插件的元数据（`PluginMetaData`）有 `is_mock` 字段：

- `pluginId = "etest.plugin.device.mock_serial"` -> `is_mock = true` -> Mock 设备
- `pluginId = "etest.plugin.device.serial_pxi"` -> `is_mock = false` -> 真实设备

加载拓扑时通过 pluginId 反查 `is_mock`，即可知道每个设备是 Mock 还是真实，进而确定整体模式。

### 4.2 一致性校验

加载拓扑时校验所有设备的 `is_mock` 必须一致：

- 全部 `is_mock = true` -> Mock 模式 -> 构建 MockUUT
- 全部 `is_mock = false` -> 真实模式 -> 不构建 MockUUT
- 混合 -> 拒绝运行，提示用户

### 4.3 设备实例化时机

设备实例化发生在**拓扑加载时**（项目打开或拓扑文件变化），不是运行时：

```
项目打开 / 拓扑文件变化
  └─ syncProjectTopologies()
       └─ engine_->loadTopology(etopoPath)
            ├─ hw_manager_->loadFromTopology(root)    // 实例化设备，填充 device_pool_
            └─ if Mock 模式:
                 hw_manager_->setMockUUT(...)          // 注入 MockUUT
```

`device_pool_` 在此时填满 Mock 插件或真实插件，`mock_uuts_` 也已注入。后续所有运行复用这套设备池。

## 6. 关键设计决策记录

| 决策 | 说明 |
|---|---|
| 模式是全局二值的 | 物理约束决定，不存在逐设备选择 |
| 模式由拓扑插件类型决定 | 不需要运行时 checkbox 切换，pluginId 隐含 is_mock |
| 混合模式拒绝运行 | 跨 Mock/真实的信号链路物理不通 |
| 协议与模式无关 | ICD 在两种模式下完全一样 |
| 设备在拓扑加载时实例化 | 项目打开时填满 device_pool_，运行时复用 |
| Mock 配置平铺在 topology/ 目录下 | `topology/MockResponses.emock`（与 `topology.etopo` 同级） |
