# 监听器订阅与运行数据生命周期重构

## 问题陈述

目前 MonitorManager 隶属于 TestExecutionEngine，引擎在 runNextInQueue 中销毁重建时，`subscribers_`（通道订阅）和 `buffer_`（采样数据）随之丢失。虽通过 `restoreMonitorUi()` 尝试恢复，但存在以下问题：

1. **订阅恢复脆弱**：强依赖 `VisualizationArea::activeChannels()` 的 `(mi, ci)` 索引，引擎重建后 MonitorManager 重新加载拓扑，多拓扑场景下 mi（monitorIndex）的对应关系可能偏移
2. **频内数据丢**：QueuedConnection 信号来不及处理时，引擎销毁导致排队事件被 Qt 清空，数据永远到不了 visualizer
3. **buffer_ 随引擎销毁**：运行中采集的数据只在引擎存活期内有效，运行结束即消失，无法用于回顾

## 现状架构

```
TestExecutionEngine
  └── MonitorManager (QObject, 主线程)
        ├── lookup_table_ [生存期: 引擎创建→销毁]
        ├── subscribers_  [生存期: 引擎创建→销毁]  ← 问题
        └── buffer_       [生存期: 引擎创建→销毁]  ← 问题

数据流:
StepRunner (worker 线程)
  → emit hardwareOperationFinished (QueuedConnection)
  → MonitorManager::onHardwareOpFinished (主线程)
  → 查 lookup_table_ → 查 subscribers_ → visualizer::onSampleCaptured
  → buffer_ 追加

引擎重建时:
  destroyEngine → MonitorManager::~MonitorManager → subscribers_/buffer_ 清零
  createEngine → 新的 MonitorManager
  restoreMonitorUi() → 尝试恢复订阅 (依赖 activeChannels, 脆弱)
```

## 讨论顺序

1. **`subscribers_` 的问题** —— 订阅是否应该存在引擎内部？如何让订阅跨引擎重建保持？
2. **`buffer_` 的问题** —— 采样数据是否应该独立于引擎？如何保证数据不因引擎销毁而丢失？

## 根因分析

当前架构将 **三种不同生命周期** 的数据绑定在同一个对象的生存期内：

| 数据 | 变化频率 | 应属生存期 | 当前绑定 |
|------|---------|-----------|---------|
| `lookup_table_` | 极低（用户编辑拓扑） | 项目级，跨运行 | 引擎级 ❌ |
| `subscribers_` | 低（用户勾选） | 应用级，跨引擎 | 引擎级 ❌ |
| `buffer_` | 高（每次运行产生） | 项目级，跨运行 | 引擎级 ❌ |

三者被硬绑定在 `TestExecutionEngine` 的生命周期中，引擎在 `runNextInQueue` 中销毁重建时，`subscribers_` 和 `buffer_` 随之丢失。

## 推荐方案：MonitorManager 移出引擎

**核心思想**：按数据生存期拆分对象归属，MonitorManager 由 `ExecutionPanelController` 直接持有，不再作为 `TestExecutionEngine` 的子对象。

### 设计来源

本方案与 `docs/thinking/IATP_设计方案.md` 中的 ICD 层设计一致。IATP 设计文档定义了 **SignalValueCache (CVT)** 和 **DataPool Pub/Sub** 机制：

> HAL(收硬件数据) → ICD内部DataPool → ICD.Subscribe() → 协议解包 → SignalValue
> → CVT (Engine.getSignal 快速读取)
> → UI监控订阅

CVT 和 Pub/Sub 都是 ICD 层的职责，与 Engine 层解耦。当前 MonitorManager 的三块数据（lookup_table_、subscribers_、buffer_）本质上是 CVT + 信号路由 + Pub/Sub 的简化实现，不应绑定在引擎的生命周期中。

### 新架构

```
ExecutionPanelController [生存期: 应用运行期间，不重建]
  ├── MonitorManager        [lookup_table_ + subscribers_ 常驻]
  │     └── buffer_         [常驻，不清除]
  ├── VisualizationArea     [可视化组件常驻]
  ├── SignalTreePanel       [树 + 勾选常驻]
  └── TestExecutionEngine   [生存期: 每次运行，可重建]
        └── start() 时连接 StepRunner 到外部的 MonitorManager
```

### 关键变化

| 变化 | 说明 |
|------|------|
| `MonitorManager` 的父对象从 `TestExecutionEngine` 改为 `ExecutionPanelController` | 引擎析构时不销毁 MonitorManager |
| `TestExecutionEngine` 通过指针访问 `MonitorManager` | `start()` 中连接信号时指向外部对象 |
| `subscribers_` 自然跨引擎保持 | 不再需要 `restoreMonitorUi()` |
| `buffer_` 跨引擎保持 | 运行结束后数据保留，可供回顾或 saveReport |
| 删除 `restoreMonitorUi()` | 不再需要恢复订阅 |
| `syncProjectTopologies()` 在引擎创建后同步 `lookup_table_` | 引擎重建时拓扑可能变化，需要同步 |

### 数据流（不变的部分）

```
StepRunner (worker 线程)
  → emit hardwareOperationFinished (QueuedConnection)
  → MonitorManager::onHardwareOpFinished (主线程)  [MonitorManager 不随引擎销毁]
  → 查 lookup_table_ → 查 subscribers_ → visualizer::onSampleCaptured
  → buffer_ 追加
```

### 数据流（引擎重建时）

```
runNextInQueue:
  destroyEngine     → 引擎析构，MonitorManager 不动 ✅
  createEngine      → 新引擎，MonitoriManager 指针注入
  engine->setMonitorManager(mm)  → 新引擎持有同一 MonitorManager 指针
  syncProjectTopologies() → 重载 lookup_table_（mtime 变化时才重建）
  start()           → 连接 StepRunner 信号到 MonitorManager
  → subscribers_ 无需恢复，就在那里 ✅
  → buffer_ 保留上次运行数据 ✅
```

### 改动范围

| 文件 | 改动 |
|------|------|
| `TestExecutionEngine.h/.cpp` | 移除 `monitor_manager_` 的 `unique_ptr`，改为原始指针 `MonitorManager*`；新增 `setMonitorManager(MonitorManager*)` |
| `ExecutionPanelController.h/.cpp` | 新增 `MonitorManager* monitor_manager_` 成员 + `monitorManager()` 访问器；创建 MonitorManager 实例，注入到引擎；所有 `engine_->monitorManager()` 改为 `monitorManager()`；`syncProjectTopologies()` 直接调 `mm->loadFromTopology()`；`destroyEngine()` 不再清 `subscribers_`；移除 `restoreMonitorUi()`；新增 `clearMonitorState()`（调 `mm->clearStructure()` + `mm->clearRuntime()`） |
| `MonitorManager.h/.cpp` | 父对象变更为 `ExecutionPanelController`；buffer_ 类型改为 `QHash`（CVT 覆盖写），新增 `history_buffer_`/FlushTimer/pendingFlush_/flush()/clearData() |
| `engine/TestExecutionEngine.cpp` | `start()` 中的信号连接指向外部的 `monitor_manager_` |

## 讨论：数据批量刷新（防 UI 线程积压）

### 问题

QueuedConnection 将每个采样点独立投递到 UI 线程。高频场景（如 AD LOOP 512 次/4ms）下 UI 线程来不及逐点处理，事件队列积压。测试结束后一次性处理时 QCustomPlot 大量 replot 导致卡顿。

### 决策（已采纳）：定时器批处理，30fps 刷新

不在 `onHardwareOpFinished` 中逐点推送给 visualizer，改为：

```
onHardwareOpFinished(mi, ci, engValue)
  → buffer_ 追加（同一 mi/ci 的最新值覆盖旧值，保留最新即可绘制波形）
  → 标记 pendingFlush_ = true
  → 不直接调 visualizer（不积压 QuenedConnection）

FlushTimer (30fps, ~33ms 间隔)
  → if (!pendingFlush_) return
  → 遍历 subscribers_，批量推最新数据给 visualizer
  → visualizer 更新 QCustomPlot 并 replot（一帧刷新，非逐点）
  → pendingFlush_ = false
```

**优点**：
- 实时可见——波形以 30fps 平滑更新，不是跑完才蹦出来
- 无事件积压——512 点合并为约 15 次批量刷新
- QCustomPlot 不 overload——一帧只 replot 一次
- MonitorManager 移出引擎后定时器不受引擎重建影响

**代价**：
- MonitorManager 新增 QTimer（33ms 间隔）
- buffer_ 需要支持 per-channel 最新值覆盖（CVT 语义）
- pendingFlush_ 标记 + 批量推送逻辑

### 优点

1. **删除整个 `restoreMonitorUi()`** —— 不再需要"恢复"订阅
2. **删除 `onProjectClosed()` 中清理 SignalTreePanel/VisualizationArea 的代码** —— 它们本来就是常驻的，与引擎无关
3. **AD LOOP 512 次数据不丢** —— QueuedConnection 事件的接收方（MonitorManager）不会被销毁
4. **波形实时渲染** —— 30fps 定时器批处理，不卡 UI

## 补充决策 1：buffer_ 改为 CVT 模式

`buffer_` 当前为 `QList<MonitorSample>`，每次 `onHardwareOpFinished` 追加，永不 trim。长时间运行（如 1 小时、每秒 1000 点）内存无上限增长。

**方案 A（已采纳）**：双轨设计——CVT 用于实时显示，append-only 历史 buffer 用于报告。

审查发现 flushSamples() 依赖全部历史采样，CVT 只保留最新值两者不可兼得。双轨分离：

| buffer | 类型 | 写入模式 | 用途 | 上限 |
|--------|------|---------|------|------|
| `buffer_`（CVT） | `QHash<QPair<int,int>, MonitorSample>` | 覆盖写 | 实时显示，定时器推 visualizer | O(通道数) |
| `history_buffer_` | `QList<MonitorSample>` | 追加写 | flushSamples 生成 .etlog | 50000 条，超出删最旧 |

**命中式**：
- `onHardwareOpFinished` → 同时写入 buffer_（覆盖）+ history_buffer_（追加）
- 定时器批处理 → 读取 buffer_，推 visualizer
- `flushSamples()` → 读取 history_buffer_，生成报告
- `clearRuntime()` → 清两者
- `clearData()` → 只清 buffer_（波形归零），不清 history_buffer_（报告不受影响）

## 补充决策 2：LOOP DELAY 临时保留

当前测试程序中的 DELAY 1ms 是规避 QueuedConnection 积压的临时补丁。

**方案 A（已采纳）**：保留 DELAY 直到 30fps 定时器批处理实现后再移除。

| 方案 | 说明 |
|------|------|
| A: 保留至定时器就绪（推荐） | 稳定优先，不影响功能 |
| B: 立即移除 | 定时器未实现，LOOP 4ms 跑完 UI 来不及，数据丢 |
| C: 调更短（0.1ms） | 执行时间 50ms，UI 仍可能来不及 |

## 补充决策 3：监听器依附于拓扑连线创建

### 当前问题

监听器的 tap 独立定义 `(deviceName, devicePort)`，不和拓扑中的 `connections[]` 关联。未连线的通道在 SignalTreePanel 中仍可勾选，但永远收不到数据，对用户产生误导。

### 目标

监听器只能从拓扑连线创建，表达"监听这条数据通路"的语义。

### 交互设计

#### 拓扑编辑器中的视觉布局

```
                                 ┌────────────────────────────┐
                                 │       综合仿真UUT           │
  ┌──────────┐       ┌────┐     │  ┌─ 串口控制口 ─────────┐  │
  │ AD采集卡 ├──[M]──┤    │     │  ├─ CAN总线口 ──────────┤  │
  │ :ai0     │       │    │     │  ├─ A429总线口 ─────────┤  │
  └──────────┘       │    │     │  ├─ AD采集口 ───────────┤  │
  ┌──────────┐       │    │     │  └─ DA输出口 ───────────┘  │
  │ DA输出卡 ├──[M]──┤    │     └────────────────────────────┘
  │ :ao0     │       │    │     
  └──────────┘       └────┘     [M] = 监听器 badge 图标
```

监听器在连线上用小圆点或小方块 badge（如字母"M"）表示，依附于连线中点附近，不占画布多余空间。

#### 创建：右键连线 → "添加监听器"

```
  ┌─────────────────────┐
  │ 添加监听器            │  ← 右键连线弹出菜单
  │ 删除连线              │
  │ 编辑属性              │
  └─────────────────────┘
```

点击后创建监听器，自动从连线派生所属关系，并弹出配置面板：

```
  ┌─────────────────────────┐
  │ 新建监听器               │
  ├─────────────────────────┤
  │ 名称: [ Monitor-AD   ]  │  ← 默认 "Monitor-{设备名}"
  │                         │
  │ 所属连线: (只读)         │
  │   AD采集卡:ai0 → UUT    │  ← 自动填入
  │                         │
  │ 显示模式: [ waveform ▼] │  ← waveform/led/meter/frame
  │                         │
  │ [✓ 创建]  [✕ 取消]      │
  └─────────────────────────┘
```

#### 编辑：点击 badge [M]

选中监听器，属性面板显示配置信息，可编辑名称和显示模式：

```
  ┌─────────────────────────┐
  │ 监听器属性               │
  ├─────────────────────────┤
  │ 名称: [ Monitor-AD   ]  │  ← 可编辑
  │                         │
  │ 所属连线: (只读)         │
  │   AD采集卡:ai0 → UUT    │
  │                         │
  │ 显示模式: [ waveform ▼] │
  │                         │
  │ [✕ 删除此监听器]         │
  └─────────────────────────┘
```

复用现有 `PropertyPanelWidget::showPropertiesFor(QGraphicsItem*)` 机制，和设备/UUT 节点行为一致——选中显示属性、创建弹窗配置。

#### 运行页 SignalTreePanel

```
  Monitor-AD (AD采集卡:ai0 → UUT)         ← 一个监听器 = 一条通路
  ├── AD采样值.采样值    [☑]               ← 信号从 ICD 自动解析
  ├── AD采样值.通道号    [□]
  
  Monitor-DA (DA输出卡:ao0 → UUT)
  ├── DA输出电压.通道号  [□]
  └── DA输出电压.电压值  [□]
```

信号列表不再由 taps 配置，改为从 `connectionId → connection → devicePort → boundFrames → ICD 帧 → 信号节点` 自动解析。

#### 删除连线时的级联行为

```
删除连线 → 检查 monitors[] 中 connectionId 匹配的监听器
  → 弹出确认: "将同时删除 X 个关联的监听器"
  → 确认后: RemoveConnectionCommand 保存整个 monitor 到命令栈（支持 undo）
  → 取消: 不操作
```

### 拓扑文件格式变更

当前 `.etopo` 格式：

```json
{
  "connections": [
    { "device": "8通道AD采集卡", "devicePort": "ai0", "product": "综合仿真UUT", "port": "AD采集口" }
  ],
  "monitors": [
    {
      "name": "Monitor-4CH_01",
      "channelCount": 4,
      "taps": [
        { "deviceName": "8通道AD采集卡", "devicePort": "ai0", "portName": "AD采集口", "productName": "综合仿真UUT" }
      ]
    }
  ]
}
```

改为：

```json
{
  "connections": [
    {
      "id": "conn-1",
      "device": "8通道AD采集卡", "devicePort": "ai0",
      "product": "综合仿真UUT", "port": "AD采集口"
    }
  ],
  "monitors": [
    {
      "name": "Monitor-AD",
      "connectionId": "conn-1",          // ← 引用连线 ID
      "displayMode": "waveform"
    }
  ]
}
```

tap 信息从 `connections[conn-1]` 派生，不再独立存储。`deviceName`、`devicePort`、`productName`、`portName` 全部从连线获取，消除不一致。`channelCount` 和 `deviceType` 不再由用户配置，改为从 `connectionId → device → port → 设备类型 + 通道容量` 自动派生。`taps[]` 字段废弃，tap 的路由信息改从 connection 绑定帧派生。

**`TopologyConnection` 新增 `id` 字段**（审查修复）：`QString id`，构造时 `QUuid::createUuid().toString()`。序列化/反序列化增加 `id` 读写。旧文件加载时没有 `id` 的连线自动补一个 UUID。UUID 不因改名而失效，与项目整体的 UUID 信号标识体系一致。

### 不向后兼容

项目未正式发布，旧 `.etopo` 文件不做兼容处理。旧文件中的 `monitors[].taps[]` 在加载时被忽略，用户需重新从连线创建监听器。

### 属性面板设计

监听器依附于连线，不再是独立的多通道设备。属性面板简化为：

```
┌──────────────────────────────┐
│ 监听器属性                    │
├──────────────────────────────┤
│ 名称: [    Monitor-AD     ]  │
│                              │
│ 所属连线: (只读)              │
│   8通道AD采集卡:ai0 → UUT    │
│                              │
│ 显示模式: [  waveform ▼  ]   │
│                              │
│ [✕ 删除此监听器]              │
└──────────────────────────────┘
```

| 字段 | 说明 |
|------|------|
| 名称 | 用户命名，默认 `Monitor-{设备名}` |
| 所属连线 | 从 `connectionId` 派生 `(device:port) → (product:port)`，只读 |
| 显示模式 | waveform/led/meter/frame，决定运行时可视化组件类型 |

`channelCount` 和 `deviceType` 不再由用户配置，改为从 `connectionId → connection → device → port` 自动派生。`channelCount` 从设备端口的通道容量获取，`deviceType` 从设备的 `type` 字段获取，填充到 `MonitorTreeEntry` 中供 SignalTreePanel 建树。

`taps[]` 字段废弃。`channelCount` 和 `deviceType` 不再由用户配置，改为自动派生（见上文）。

### 影响范围

| 模块 | 改动 |
|------|------|
| `.etopo` 格式 | `connections` 加 `id` 字段；`monitors[].taps[]` 改为 `monitors[].connectionId` |
| `parseTopology()` / `appendFromTopology()` | 不再解析 taps，改为从 connection 派生 |
| `MonitorTreeEntry` | tap 信息由 connection 填充，结构不变 |
| 拓扑编辑器 | 连线右键菜单 + 添加监听器命令 + 删除连线时级联删除 |
| 拓扑编辑器 | 监听器在画布上的位置/样式调整（依附于连线显示） |
| `MonitorManager` | lookup_table_ 的填充方式变更：不再从 `monitors[].taps[]` 读取，改为从 `connectionId → connection → (deviceId, devicePort)` 派生。key 格式不变 `(deviceId, devicePort)` |
| 向后兼容 | 不保留 |

### 代价

| 代价 | 说明 |
|------|------|
| `RemoveConnectionCommand` 级联删除 monitor（审查修复） | 执行时检查 `monitors[]` 中 `connectionId` 匹配的 monitor，整个保存到命令中，undo 时恢复、redo 再删。提示"将删除 X 个关联的监听器" |
| 引擎不再独占 MonitorManager | 需要处理引擎和 MonitorManager 的同步（start/stop 时） |
| `clearTopologyState()` 需要调整 | 不再销毁 MonitorManager，只清 lookup_table_ + buffer_ |
| 信号连接在引擎 start/stop 时需要管理 | 避免引擎停止后信号还连着 MonitorManager |
| 现有 `engine_->monitorManager()` 调用方需确认 | `ExecutionPanelController` 多处用了 `engine_->monitorManager()` |

## 实施计划

### 阶段划分

按底层到上层分 3 个阶段，每阶段可独立编译验证。

#### 阶段 1 — MonitorManager 移出引擎（核心重构）

- `TestExecutionEngine.h`：`unique_ptr<MonitorManager>` → `MonitorManager*`，新增 `setMonitorManager(MonitorManager*)`
- `TestExecutionEngine.cpp`：`initEngine()` 不再创建 MonitorManager；`start()` 中信号连接指向外部的 monitor_manager_ 指针；`clearTopologyState()` 不再清 monitor
- `ExecutionPanelController.h`：新增 `MonitorManager* monitor_manager_` 成员 + `monitorManager()` 访问器
- `ExecutionPanelController.cpp`：postInit 中创建 MonitorManager 并注入引擎；所有 `engine_->monitorManager()` → `monitorManager()`；删除 `restoreMonitorUi()`
- `syncProjectTopologies()` 改为直接操作 `monitor_manager_` 而非通过引擎
- 新增 `clearMonitorState()` 方法
- 删除 `onProjectClosed()` 中清理 SignalTreePanel/VisualizationArea 的代码
- 编译验证 + 跑测试

#### 阶段 2 — buffer_ 重构（CVT + 定时器批处理 + history_buffer）

- `MonitorManager.h`：`buffer_` 从 `QList` 改为 `QHash<QPair<int,int>, MonitorSample>`；新增 `history_buffer_: QList<MonitorSample>`；新增 `FlushTimer* flush_timer_`；新增 `pendingFlush_: bool`
- `MonitorManager.cpp`：`onHardwareOpFinished()` 双轨写入（CVT 覆盖 + history 追加）；`flushSamples()` 读取源改为 `history_buffer_`；新增定时器回调 `flush()`，批量推 subscribers_；新增 `clearData()`（只清 CVT）

##### 子任务 B：连线 badge 图标

**文件**：`src/topology/ConnectionItem`（`topology_items.h/.cpp`）

- 在 `ConnectionItem` 上用 `paint()` 直接绘制 badge 小圆点（不创建独立的子 QGraphicsItem）
- 当该连线有 monitor 引用时显示 badge，无 monitor 时隐藏
- badge 位置：连线中点附近
- badge 外观：小圆形，字母 "M"，半透明
- badge 点击行为：选中对应的 `MonitorItem`，显示属性面板

**为什么不创建子 QGraphicsItem**：`PropertyPanelWidget::showPropertiesFor()` 通过 `qgraphicsitem_cast<MonitorItem*>(item)` 识别监听器。独立的 badge 子 item 不是 `MonitorItem`，无法触发属性面板。故采用 `paint()` 直接绘制 + `ConnectionItem::mousePressEvent()` 中检测点击位置是否在 badge 区域内，然后通知 scene/editor 选中对应的监听器。

**实现方式**：
- 添加成员 `bool has_monitor_ = false;` + `int monitor_index_ = -1;`
- 添加 `void setMonitorState(bool hasMonitor, int monitorIndex)` 方法
- `paint()` 中在连线中点位置画小圆形 badge + "M" 字母
- `mousePressEvent()` 中判断点击位置是否在 badge 区域内，是则通过 `QGraphicsScene::selectedItems` 或发射信号通知选中对应的监听器
- 监听 `TopologyDocument` 的 `monitorAdded`/`monitorRemoved` 信号，检查 `connectionId` 是否匹配当前连线
- `ConnectionItem` 当前无 `mousePressEvent` 重写，需在 header 新增声明（审查 B2）
- `boundingRect()` 在 `has_monitor_` 为 true 时需扩展 margin 以包含 badge 绘制范围，防裁剪（审查 A1）
