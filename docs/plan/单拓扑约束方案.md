# 单拓扑约束方案

> **日期**: 2026-07-28
> **状态**: 设计讨论中
> **关联**: `docs/plan/Mock模式推断与配置方案.md`、`docs/01-规划/测试执行业务流程.md`、`docs/plan/MockUUTSimulator设计.md`

## 1. 背景与问题

### 1.1 物理模型

ETest 平台的物理使用场景：

```
一台工控机（运行 IDE）
  ├── 插槽1: PXI-CAN 卡（ch1/ch2/ch3）
  ├── 插槽2: PXI-A429 卡（ch1/ch2/ch3）
  ├── 插槽3: PXI-AD 采集卡
  └── ...
      │
      │ 物理线缆
      ▼
  UUT（被测设备）
      ├── 飞控#1 ← CAN卡.ch1 + A429卡.ch1 + AD卡.ch0
      ├── 飞控#2 ← CAN卡.ch2 + A429卡.ch2 + AD卡.ch1
      └── 飞控#3 ← CAN卡.ch3 + A429卡.ch3 + AD卡.ch2
```

**一台工控机 = 一个测试场景 = 一个拓扑**。工控机上的硬件设备插槽和通道组合是固定的，物理换场景需要重新插拔线缆，软件上的"多拓扑"并不能避免物理操作。

### 1.2 多 UUT 场景

一台工控机通过硬件设备的不同通道组合，控制多个相同或不同的 UUT。这在**一个拓扑内**就能表达：

```json
{
  "products": [
    { "name": "飞控#1", "ports": [...] },
    { "name": "飞控#2", "ports": [...] },
    { "name": "飞控#3", "ports": [...] }
  ],
  "devices": [
    { "id": "pxi-can", "ports": [{ "name": "ch1" }, { "name": "ch2" }, { "name": "ch3" }] },
    { "id": "pxi-a429", "ports": [...] },
    { "id": "pxi-ad", "ports": [...] }
  ],
  "connections": [
    { "productName": "飞控#1", "port": "CAN", "deviceName": "pxi-can", "devicePort": "ch1" },
    { "productName": "飞控#2", "port": "CAN", "deviceName": "pxi-can", "devicePort": "ch2" },
    { "productName": "飞控#3", "port": "CAN", "deviceName": "pxi-can", "devicePort": "ch3" }
  ]
}
```

不需要多个拓扑文件。

### 1.3 当前多拓扑架构的问题

当前 `syncProjectTopologies` 扫描 `topology/` 目录下所有 `.etopo` 文件，循环加载，引入了一系列"累积/合并"逻辑：

| 模块 | 多拓扑引入的复杂度 | 风险 |
|---|---|---|
| 拓扑加载 | 循环加载多个 .etopo，变化检测需逐文件比较 mtime | 逻辑复杂，边界条件多 |
| 设备池 | 多拓扑设备累积到同一 `device_pool_` | 设备 ID 冲突风险 |
| MockUUT | 多拓扑 MockUUT 累积到同一 `mock_uuts_` | UUT 定位歧义 |
| 监听器 | `appendFromTopology` 累积合并 | 重复累积、语义不一致（append vs 覆盖） |
| Mock 配置 | 共享一个 MockResponses.json，需 `productName+deviceId` 在多拓扑间区分 | 误匹配风险 |
| 拓扑变化 | 全量重建（`clearTopologyState` + 重新加载所有 .etopo） | 重建开销大 |

这些"累积"逻辑是 bug 的温床 -- `appendFromTopology`（累积）和 `loadFromTopology`（覆盖）的语义不一致，多拓扑合并时设备 ID 冲突、monitor 重复累积等问题隐含其中。

### 1.4 设计推导

拓扑这个概念串联起来了硬件（硬件上的端口）以及抽象的概念 UUT。在拓扑的基础上，绑定了 ICD 协议的帧到激励设备的端口上，表明信号在激励设备的端口上是如何填充发送以及如何接收到后解包的。

一个测试工程中应该仅仅只能有一个拓扑文件，这个拓扑文件中可以有多个激励设备（测试就是组合不同的激励设备给被测设备通讯）和多个 UUT（UUT 可以一样，也可以不一样）。

激励设备被物理上安装到工控机上，ETestStudio 运行在工控机上。把工控机看成一个整体（包括插上去的各种硬件设备），工控机和 UUT 之间通过物理上的线缆连接。一个测试场景下，这个物理上的组合是固定的（插拔线缆的事儿程序不管）。因此使用一个拓扑文件就能够描述这样的测试场景，单拓扑文件的设定成立。

> **范围假设**：本推导基于「单工控机运行单 ETestStudio 实例」的场景，不覆盖多工控机协调或分布式测试。

## 2. 方案：限制一个项目一个拓扑

### 2.1 核心约束

**一个项目只能有一个拓扑文件，文件名固定为 `topology.etopo`，一个拓扑可以有多个 UUT（products[]）。**

```
项目结构
├── topology/
│   └── topology.etopo        ← 唯一的拓扑文件（固定文件名）
├── protocols/               ← ICD 协议（独立资产，与拓扑解耦）
│   ├── frame_a.eprotox
│   └── frame_b.eprotox
├── programs/                ← 测试程序
│   └── test.tcase
```

固定文件名的好处：
- 代码直接拼路径 `topology/topology.etopo`，不需要 `entryInfoList` 扫描目录
- `topo_mtimes_` 彻底移除，mtime 检查只需 `QFileInfo(path).lastModified()`
- 从代码层面保证单拓扑，用户无法让引擎加载第二个 .etopo

**其他 .etopo 文件的处理**：引擎始终只加载 `topology/topology.etopo`，目录下其他 .etopo 文件（备份、草稿等）在输出面板警告提示「检测到多余 .etopo 文件，已忽略」，不阻止运行。用户可自由存放参考文件。

### 2.2 物理模型对应

| 物理世界 | 软件模型 |
|---|---|
| 一台工控机 | 一个项目 |
| 工控机上的硬件设备组合 | 一个拓扑文件（.etopo） |
| 硬件设备连线的 UUT | 拓扑中的 products[] |
| 一组 ICD 协议规范 | protocols/ 下的 .eprotox 文件 |
| 测试流程脚本 | programs/ 下的 .tcase 文件 |

### 2.3 多 UUT 不受限

`products[]` 是数组，支持任意 UUT 组合：
- 全部相同（如 3 台一模一样的飞控）
- 全部不同（如 1 台飞控 + 1 台电源 + 1 台导光板）
- 混合（如 2 台相同飞控 + 2 台相同电源 + 1 台导光板）

一台工控机通过不同通道组合控制多个 UUT 的场景，在一个拓扑内完整表达。

## 3. 连锁简化分析

### 3.1 引擎层

| 当前 | 简化后 |
|---|---|
| `syncProjectTopologies` 循环加载多个 .etopo（`ExecutionPanelController.cpp:441/486`） | 加载唯一的 .etopo |
| `topo_mtimes_`（`QHash<QString, QDateTime>`，`ExecutionPanelController.h:178`）记录多文件 mtime 并逐个比较（行 465-470） | 单文件 mtime 比较，去掉 `topo_mtimes_` |
| `clearTopologyState`（`TestExecutionEngine.cpp:99-105`）+ 重新加载所有 .etopo | 单文件重建 |
| `monitor_manager_->appendFromTopology(root)`（`TestExecutionEngine.cpp:178`）累积 | 改为 `loadFromTopology(root)` 覆盖（`MonitorManager` 已有此方法，内部先 `clearStructure` + `clearRuntime` 再 `appendFromTopology`） |
| `HardwareManager::loadFromTopology` 被多次调用，设备累积 | 一次性加载 |

### 3.2 监听器

`MonitorManager` 当前有两个加载方法（`MonitorManager.h:43-44`）：

- `loadFromTopology`：覆盖语义（先 `clearStructure()` + `clearRuntime()` 再 `appendFromTopology`）
- `appendFromTopology`：累积语义（`indexOffset = tree_cache_.size()` 偏移，不清理已有数据）

`TestExecutionEngine::loadTopology` 当前调用的是 `appendFromTopology`（累积），用于多拓扑合并。单拓扑约束后直接改用 `loadFromTopology`（覆盖），消除 `indexOffset` 偏移逻辑和累积合并风险。

`appendFromTopology` 方法可保留（内部复用），但外部调用点统一为 `loadFromTopology`。

> **注意**：`HardwareManager::loadFromTopology`（`HardwareManager.cpp:37`）本身不清理已有设备池，依赖外部 `clearTopologyState` 调用 `hw_manager_->closeAllDevices()` 来清理。这与 `MonitorManager::loadFromTopology`（内部自带清理）不对称。单拓扑下只调用一次所以无实际问题，但若未来扩展需注意此差异。

### 3.3 测试程序

信号引用来自唯一拓扑，`deviceId` 无跨拓扑歧义。

### 3.4 项目结构

`topology/` 目录下只允许一个 .etopo，项目结构树组织更清晰。

### 3.5 独立工具

`test-executor`（`src/tools/test-executor/main.cpp:565`）和 `test-executor-cli`（`src/tools/test-executor-cli/main.cpp:506`）通过命令行 `--topology` 参数接受任意 .etopo 路径，各自只调用一次 `loadTopology`。引擎层 `appendFromTopology` -> `loadFromTopology` 的改动对它们行为无影响（单次调用语义不变）。独立工具属于命令行执行器，不纳入项目级单拓扑约束，仍可加载任意 .etopo 路径。

## 4. 影响范围

### 4.1 引擎层（`src/engine/`）

- `TestExecutionEngine::loadTopology`：保持单次加载语义，不再依赖外部循环调用
- `TestExecutionEngine::clearTopologyState`：函数不变（本就只清单个拓扑状态），调用上下文简化（调用方不再循环调用）

### 4.2 应用层（`src/app/`）

- `ExecutionPanelController::syncProjectTopologies`（`ExecutionPanelController.cpp:413-493`）：
  - 当前行为：扫描 `topology/` 目录（行 421-429），for 循环逐个 `loadTopology`，不报错不警告
  - 简化后：只加载 `topology/topology.etopo`，其他 .etopo 在输出面板警告提示
  - 首次加载分支（行 438-451）：去掉 `for` 循环，单文件加载
  - 变化检测分支（行 464-480）：单文件 mtime 比较，去掉 `topo_mtimes_` 的多文件遍历
  - 全量重建分支（行 482-492）：去掉 `for` 循环，单文件重建；`clearMonitorState()`（行 484）变为冗余（`loadFromTopology` 内部已清理），可移除
- `ExecutionPanelController::topo_mtimes_`（`ExecutionPanelController.h:178-179`）：可移除或简化为单个 `QDateTime`
- `ExecutionPanelController::clearMonitorState`：全量重建分支中的调用可移除（见上），方法本身保留供其他调用方使用

### 4.3 监听器（`src/engine/MonitorManager`）

- `TestExecutionEngine::loadTopology`（`TestExecutionEngine.cpp:178`）中 `appendFromTopology` 改为 `loadFromTopology`
- `loadFromTopology`（`MonitorManager.cpp:33`）已实现覆盖语义（`clearStructure` + `clearRuntime` + `appendFromTopology`），无需新增方法
- `appendFromTopology` 的 `indexOffset` 偏移逻辑（`MonitorManager.cpp:41`）在单拓扑下 `indexOffset` 恒为 0，可保留不改（内部复用安全）

### 4.4 拓扑编辑器（`src/topology/`）

- 无功能改动
- 约束只在引擎层（`syncProjectTopologies` 只加载 `topology/topology.etopo`），拓扑编辑器不感知单拓扑约束
- 用户通过编辑器"另存为"创建的其他 .etopo 文件，引擎自然忽略，不影响运行

### 4.5 UI 层影响

单拓扑约束不止引擎层，UI 交互也有一串连锁改动。以下均经代码核实：

| UI 位置 | 当前行为（已核实） | 单拓扑后 |
|---|---|---|
| 侧边活动栏 | 有「拓扑」按钮（`MainWindow.cpp:1086`，`PageId::kTopology`），点击切换到侧边栏拓扑管理页 | 按钮可保留，管理页内容简化为直接打开 `topology.etopo` |
| 侧边栏 | 有 `TopologyManagerWidget`（`MainWindow.cpp:1104`），列出 topology/ 下所有 .etopo，双击打开 | 简化为直接打开 `topology.etopo`，无需列表选择 |
| 项目树右键菜单 | 「拓扑」分类节点右键有「新建拓扑文件」（`ProjectStructureWidget.cpp:492-494` 配置驱动） | 已存在 `topology.etopo` 时「新建」需禁用或改为「重置拓扑」（清空内容） |
| 拓扑管理页工具栏 | `TopologyManagerWidget` 有独立的「新建拓扑」按钮（`TopologyManagerWidget.cpp:77` `topologyNewBtn`，`onNewTopology()` 行 352） | 同项目树右键菜单，已存在 `topology.etopo` 时禁用或改为「重置拓扑」 |
| 项目创建 | 只创建空 `topology/` 目录，不预置 .etopo（`ProjectManager.cpp:27-62`） | 预置空 `topology/topology.etopo` |
| 项目树硬件节点 | `refreshHardwareDevices()` 扫描 topology/ 下**所有** .etopo 解析硬件设备节点（`ProjectStructureWidget.cpp:1263-1366`） | 改为只读 `topology.etopo`，不再扫描全部 .etopo |

### 4.6 项目结构

- 项目模板：`topology/` 目录下预置空 `topology.etopo`
- 项目打开时校验：`topology/` 下存在其他 .etopo 时，输出面板警告提示

## 5. 数据迁移

### 5.1 现有项目

现有项目的 .etopo 文件名可能不是 `topology.etopo`，需手动重命名。多 .etopo 项目需选择保留一个并重命名为 `topology.etopo`，其余删除或移走。

### 5.2 迁移策略

- 项目打开时检测 `topology/topology.etopo` 是否存在
- 若不存在但目录下有其他 .etopo，不自动重命名，由用户手动改名
- 新项目模板预置空 `topology/topology.etopo`，不存在迁移问题
- 迁移步骤写入文档，用户有据可查

### 5.3 异常场景处理

单拓扑下 `topology.etopo` 是唯一拓扑来源，损坏 = 完全不可用。当前 `syncProjectTopologies`（行 441、486）调用 `loadTopology` 时**忽略其返回值**，文件解析失败不会向上传播。实施时需处理以下异常场景：

| 场景 | 处理策略 |
|---|---|
| `topology/` 目录不存在或为空 | 输出面板提示「拓扑文件缺失，请创建拓扑」 |
| `topology.etopo` 不存在但目录有其他 .etopo | 提示用户手动重命名（见 5.2） |
| `topology.etopo` 存在但 JSON 解析失败 | 输出面板提示「拓扑文件损坏」，引擎不加载，不静默跳过 |

`syncProjectTopologies` 应检查 `loadTopology` 返回值，解析失败时不再继续执行后续逻辑（如 `refreshMonitorTree`），避免在不一致状态下运行。注：独立工具 `test-executor`（`main.cpp:566`）和 `test-executor-cli`（`main.cpp:507`）已正确检查返回值，此问题仅存在于主程序的 `syncProjectTopologies`。

## 6. 代价与补偿

### 6.1 失去的

- 一个项目多场景切换：不能在同一项目中切换不同拓扑运行

### 6.2 补偿

- 多场景需求通过多项目实现
- ICD 协议是独立资产（`protocols/` 目录），跨项目可复用
- 物理换场景需要重新接线，软件多拓扑并不能避免物理操作
- 多项目切换的代价（重载工程、协议/程序资产重新初始化）相比多拓扑切换更重，但这是物理换场景的固有成本，软件多拓扑不能消除

### 6.3 不受影响的

- 一个拓扑内多 UUT 不受限（`products[]` 数组）
- 测试程序、ICD 协议、监听器等功能不受限

| 2026-07-28 | 拓扑编辑器不改动 | 约束只在引擎层，固定文件名已保证单拓扑，编辑器改动可后续按需做 |
