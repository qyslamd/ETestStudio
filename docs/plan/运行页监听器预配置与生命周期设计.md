# 运行页监听器预配置与生命周期设计

> 问题发现与方案讨论记录。逐步深化决策，当前为初始状态。

## 问题陈述

加载测试项目后切换到运行页（page1），预期流程是：验证 → 选择程序 → 运行。但监听器（SignalTreePanel）只在运行期间才出现，用户没有机会在运行前预先配置要监听的通道。如果测试程序运行时间很短，监听器树一闪而过，用户根本无法配置，也看不到任何效果。

## 当前架构回顾

### 组件结构

```
运行页 (ExecutionDashboard)
├── 左列: ExecutionDebugWidget      (运行前提/进度树)
├── 中列: SignalTreePanel            (监听器信号树 ← 问题所在)
├── 右列: VisualizationArea          (可视化区)
└── 底部: QTabWidget
    ├── 输出 (ExecutionOutputPanel)
    └── 问题 (ProblemsPanel)
```

### 数据流

```
.etopo (拓扑文件)
  → TestExecutionEngine::loadTopology()
    → MonitorManager::appendFromTopology()    [填充 tree_cache_]
      → MonitorManager::monitorTree()          [返回树数据]
        → SignalTreePanel::setMonitorTree()    [构建 QTreeWidget]
```

### 当前调用时机

```
onProjectOpened
  ├── createEngine()                    ← 引擎创建，MonitorManager 为空
  ├── 扫描 topology/ → 注册设备到 SignalRegistry
  └── syncProjectTopologies() 未调用    ← 拓扑未加载到 MonitorManager

setDashboard (切到运行页时)
  ├── refreshMonitorTree()              ← MonitorManager 无数据，树为空
  └── 连接 checkStateChanged 信号

run()
  ├── syncProjectTopologies()           ← 首次加载拓扑到 MonitorManager
  ├── engine_->start()
  ├── engineStarted 信号
  ├── refreshMonitorTree()              ← 树终于有数据，但时机已晚
  └── 若程序很快结束 → 树闪一下消失
```

## 核心矛盾

监听器的**配置**是运行前的需求（用户需要预先知道有哪些通道、勾选想看哪些），但当前监听器的**数据加载**和**UI展示**都绑定在运行时，导致：

1. 切到运行页时 SignalTreePanel 无数据可展示
2. 用户无法在 run 前勾选通道
3. 如果程序运行时间短，整个交互窗口几乎为零
4. 每次 `refreshMonitorTree()` 调用 `buildTree()` 重建树，丢失前一次勾选状态

## 待讨论决策点

### 决策 1：拓扑加载时机

`syncProjectTopologies()` 应该何时执行？

- 方案 A（~~在 `createEngine()` 内部自动加载~~）
- 方案 B（~~在 `setDashboard()` 时加载~~）
- **方案 C（已采纳）**：在 `onProjectOpened()` 末尾加载，紧接 `refreshMonitorTree()`
- 方案 D（合并方案，非必须）

**理由**：
1. 审查发现 `setDashboard()` 只在 `lazyInit()` 时调用一次，不是切页回调（切页走 `central_stack_->setCurrentIndex(1)`），方案 B 不可行
2. `onProjectOpened()` 已经是项目级初始化入口：引擎、SignalRegistry、ICD 都在这里初始化，拓扑加载放这里语义对齐
3. `onProjectOpened()` 第 1525-1562 行已在扫描同一批 .etopo 文件（预注册设备到 SignalRegistry），额外加载到 MonitorManager 的开销相对于整个 `onProjectOpened()` 可以忽略
4. 不切到运行页时树数据已就绪——但用户不切到运行页也看不见，数据存在内存中无害

**影响**：
- `onProjectOpened()` 末尾（`syncControlStates()` 之前）插入 `syncProjectTopologies()` + `refreshMonitorTree()`
- `setDashboard()` 中只在 dashboard 注入后调 `refreshMonitorTree()`（此时数据已在 MonitorManager 中，树直接展示，无需重新加载拓扑）
- `run()` 中的 `syncProjectTopologies()` 调用**保留**作为 failsafe 和拓扑变化兜底
- **`clearTopologyState()` 从 `syncProjectTopologies()` 中移出**（审查修复 #1）。`syncProjectTopologies()` 不再负责清数据，只负责同步：
  - `tree_cache_` 为空 → `appendFromTopology()` 追加
  - mtime 没变 → 直接 return，不动任何东西
  - mtime 变了 → `clearStructure()` + 重新加载
- `clearTopologyState()` 保留但改实现（见决策 2 Blocker 1 修正），仅在 mtime 变化时调用

**方法改名**（审查修复 #10）：`loadProjectTopologies` 改名为 `syncProjectTopologies`，反映新语义"增量同步拓扑数据到 MonitorManager"。旧名彻底废弃，文档与代码统一用新名。

**拓扑变化检测（追加决策）**：
- 方案：`syncProjectTopologies()` 对比拓扑文件列表与时间戳
- 文件列表没变且所有 mtime 都没变 -> 跳过加载，树不动、勾选不动
- 文件列表改变（新增/删除 .etopo）或任一 mtime 改变 -> 重新加载拓扑并刷新树（进入决策 2 的"拓扑变化"分支，第三轮审查 S5）
- **mtime 状态存 `ExecutionPanelController`**（审查修复 #5）：加 `QHash<QString, QDateTime> topo_mtimes_` 成员，与 `syncProjectTopologies()` 同类。mtime 比较本质是"是否需要重新加载"的调度判断，属于 controller 职责。项目关闭时随 controller 一起清掉

### 决策 2：勾选状态保持

- **方案 A（已采纳）**：跨运行保持 — 用户勾选后，除非手动取消或拓扑结构变化，勾选一直保留
- 方案 B：运行结束自动清空
- 方案 C：持久化到项目配置

**实现方式（审查后修正）**：拆分 `MonitorManager::clear()` 为两个方法：

| 方法               | 清理范围                                         | 调用时机                |
| ------------------ | ------------------------------------------------ | ----------------------- |
| `clearRuntime()`   | `buffer_` 采样缓存                               | 运行前后 / 清空数据按钮 |
| `clearStructure()` | `tree_cache_` + `lookup_table_` + `subscribers_` | 仅拓扑结构变化时        |

**`clearStructure()` 同时清 `subscribers_`**（审查修复 #3）：拓扑变化时旧订阅中的 `(mi, ci)` 可能失效或语义改变，保留旧订阅会导致数据流向错误或悬挂回调。`clearStructure()` 后订阅空了，由"从 VisualizationArea 恢复订阅"机制重建。

**`TestExecutionEngine::clearTopologyState()` 保留但改实现**（第三轮审查 Blocker 1 修正，反转原 #2 决策）：第三轮审查发现该函数除清 MonitorManager 外，还承担 `hw_manager_->closeAllDevices()`（关闭硬件设备、防句柄泄漏）和 `topology_doc_` 重置两项职责。删除会丢失这些职责。改为：
- 内部实现改为：`topology_doc_ = {}` + `hw_manager_->closeAllDevices()` + `monitor_manager_->clearStructure()` + `monitor_manager_->clearRuntime()`
- 不再无条件调用，仅在 `syncProjectTopologies()` 的 mtime 变化分支调用（彻底重置拓扑以备重新加载）
- mtime 变化时 buffer_ 也清：旧采样数据对应旧拓扑通道，语义已错，应随结构一起清
- `closeAllDevices()` 仅在引擎 Idle 时安全（审查 L3 约束）：`syncProjectTopologies` 实际只在 onProjectOpened / run 启动前 / runNextInQueue 重建后调用，均处 Idle 态。若将来在运行中调用需先 stop 引擎，否则破坏正在进行的采集
- `MonitorManager::clear()` 仍删除（问题根因），但 `clearTopologyState()` 保留承担"彻底重置"语义

**`MonitorManager::clear()` 删除并为新方法新增测试**（第三轮审查 S2 修正原 #9）：`clear()` 是问题根因之一，删除。第三轮审查确认 `tests/engine/monitor_manager_test.cpp` 中并无 `clear()` 现有用例，故不是迁移而是新增：为 `clearRuntime()` 新增测试（清 buffer 后 tree_cache_ / subscribers_ 不变）；为 `clearStructure()` 新增测试（清 tree_cache_ / lookup_table_ / subscribers_ 后 buffer_ 不变）。

**理由**：存/恢复勾选本质上是给破坏性操作打补丁。拆 clear 从根源上避免破坏——`tree_cache_` 和 `lookup_table_` 只在拓扑结构确实变化时才重建，此时 `clearStructure()` + 在新树中恢复仍存在的通道勾选。最常见的场景（拓扑没变、多次运行）则完全跳过重建，勾选自然保持。

**加载拓扑时的路径判断**：
```txt
  |── tree_cache_ 为空（首次加载 / 引擎重建后）
  │     -> appendFromTopology() 追加
  │     -> setMonitorTree(tree, activeChannels()) 恢复勾选  [审查修复 #7 + Blocker 2]
  │     -> 从 activeChannels() 逐个 subscribe() 恢复订阅  [Blocker 2]
  │     -> 记录文件的 mtime 快照
  │
  └── tree_cache_ 非空（已有数据）
        ├── mtime 没变
        │     → 跳过（树不动、勾选不动、订阅不动）
        └── mtime 变了
              -> engine_->clearTopologyState()  [清 hw_manager 设备 + topology_doc_ + MonitorManager 结构与 runtime]
              -> 逐文件 engine_->loadTopology()  [走 appendFromTopology 重建 tree_cache_]
              -> setMonitorTree(tree, activeChannels()) 带勾选建树  [第四轮 B1 统一]
              -> 从 activeChannels() 逐个 subscribe() 恢复订阅

```

**订阅与勾选恢复统一用 `activeChannels()` 作为事实来源**（审查修复 #6 + Blocker 2）：不管是首次加载、mtime 变化还是引擎重建触发，恢复逻辑统一为 `setMonitorTree(tree, activeChannels())` + 逐个 `subscribe()`。真首次（`onProjectOpened`）`activeChannels()` 为空，退化为全 Unchecked 无订阅的正常首次展示；引擎重建（`runNextInQueue`）`activeChannels()` 非空，勾选和订阅自动恢复，跨队列项保持。一套逻辑覆盖所有路径，无需区分调用来源。

**边界情况**：
- 拓扑变化（mtime 改变）-> `clearTopologyState()` 彻底重置（清 hw_manager 设备 + topology_doc_ + MonitorManager 结构与 runtime），重建树时在新树中恢复旧勾选中的、仍然存在的 `(mi, ci)`，不存在的静默忽略
- 项目关闭 → engine 销毁、树析构，自然清空，不影响跨项目
- 跨运行保持意味着多次运行间勾选状态累积，不会因运行起停而重置
- 拓扑变化时被删通道的孤立可视化组件（审查 L2，已知 UX 限制）：恢复逻辑只对仍存在的通道重订阅，被删通道的可视化组件留在 VisualizationArea 显示陈旧数据、无新数据流入。不自动销毁（用户可能临时改拓扑不想丢配置），用户可右键关闭

**新增接口 `setMonitorTree(tree, preChecked)`，不引入 `checkedChannels()`**（独立终审 Y4 修正原 B1 措辞）：
- 决策 3 保证"勾选 ⇔ 有可视化组件"恒等，`activeChannels()`（来自常驻 VisualizationArea）是唯一事实来源
- 凡需恢复勾选的场景（首次加载/引擎重建/mtime 变化），树都已被清空，`checkedChannels()`（读树）根本读不到，故不引入（注：代码中本就不存在该方法，非"废弃"）
- 仅保留 `setMonitorTree(tree, preCheckedChannels = {})` 可选第二参数：`buildTree()` 构建每个叶节点后，检查 `(mi, ci)` 是否在 preChecked 集合中，是则 `setCheckState(Checked)`
- 所有恢复路径统一：preChecked 参数的数据源固定为 `VisualizationArea::activeChannels()`

**新增接口 `VisualizationArea::activeChannels()`**（审查修复 #4）：
- 返回 `QList<QPair<int,int>>`，遍历内部容器拆出 `(monitorIndex, channelIndex)`
- 供引擎重建（`runNextInQueue`）和拓扑变化（mtime 改变）后恢复订阅使用
- VisualizationArea 是"当前有哪些可视化组件"的事实来源，由它提供活跃通道列表

**`engineStarted` → `refreshMonitorTree()` 已移除**：
- 审查发现 `connectEngineSignals()` 中连接了 `engine_->engineStarted` → `refreshMonitorTree()`，每次引擎启动无条件重建树抛掉勾选
- 既然拓扑加载已提前到项目打开时、mtime 比较由 `syncProjectTopologies()` 统一管理，这个连接已无存在价值
- 已决策：**删掉该连接**。树刷新集中到 `syncProjectTopologies()` 的 mtime 比较逻辑中，一处判断、一处刷新

### 决策 3：订阅与可视化的生命周期

- **方案 A（已采纳）**：勾选即创建、可视化组件常驻
- 方案 B：仅运行时创建
- 方案 C：混合——勾选即创建，运行结束保留但不更新

**理由**：
1. 用户勾选通道后应立刻看到对应可视化面板（名称、通道号等），即使没数据也给占位显示"等待数据"，交互反馈即时
2. 运行结束后数据残留是正向体验——用户能回顾上次跑的波形/数值
3. 不需要复杂的冻结/恢复逻辑：有数据就画，没数据就空着，简单可靠
4. `subscribe()` 只在引擎运行时触发回调，空闲时订阅无害

**影响**：
- `checkStateChanged` 中当前已订阅 + 创建可视化组件，行为基本符合，确认即可
- 可视化组件需考虑空闲态显示（如灰色背景 + "等待数据"文本）
- 取消勾选 → 销毁可视化组件 + unsubscribe
- **引擎重建恢复订阅**（review 问题 5）：`runNextInQueue()` 中 `destroyEngine()` + `createEngine()` 后，遍历 VisualizationArea 中当前活跃的 `(mi, ci)` 列表，逐个 `subscribe()`。不需要 SignalTreePanel 参与，可视化组件常驻即是最新的"需要订阅的通道"清单

### 决策 4：运行结束时监听器树的残留状态

- **方案 A（已采纳）**：保留全部状态 — 树不动、勾选保持、可视化组件及其采样数据保持
- 方案 B：保留树和勾选，但清空可视化数据
- 方案 C：全部恢复初始态（与决策 2 冲突，排除）

**理由**：
1. 波形图/数值本身有时间戳，用户能分辨数据归属
2. 运行结束保留数据便于回顾、对比、截图
3. 下次运行新数据自然覆盖，无需人工干预
4. 已有 clear 按钮兜底，用户想清可以自己点

**影响**：
- 运行结束后 (`engineFinished` 信号) 不需要对 SignalTreePanel 和 VisualizationArea 做特殊清理
- `refreshMonitorTree()` 不应在 `engineFinished` 时触发（否则重建树丢失勾选）
- `engineStarted` 时是否刷新树需和决策 2（勾选保持）联动——如果拓扑没变，不应该重建树抛掉勾选

## 附加决策

### 附加 1：Ribbon 重置按钮

运行结束后保留数据，但用户可能需要手动清除采样数据重新观测。在 ribbon 上运行控制区（停止按钮旁）增加一个"清空数据"按钮。

- **功能范围**（轻量版）：清除所有可视化组件中的采样数据 + `MonitorManager::clearRuntime()`（清 `buffer_`）。不影响树结构、勾选状态和可视化组件本身。
- **禁用条件**：引擎处于 Running 或 Paused 状态时禁用（运行中不应干扰数据采集）
- **位置**：ribbon 运行工具栏，停止按钮右侧
- `.etlog` 报告在 `engineFinished` 时已自动生成，早于点"清空数据"的时机，所以不影响已导出的报告
- **`SignalVisualizer::clearData()` 已存在无需新增**（第三轮审查 S1 修正原 #8）：基类已声明 `virtual void clearData() = 0`，四个子类（WaveformWidget / ValueLabelWidget / DigitalMeterWidget / StateLEDWidget）均已实现。与决策 3"清数据 ≠ 销毁组件"一致
- **子类数量实施时确认**（独立终审 Y5）：`SignalVisualizer.h` 注释提到 6 个子类（含 CANFrameWidget / A429LabelWidget），但 grep 只找到 4 个实现 `clearData()`。若这两个类存在且继承 SignalVisualizer，纯虚函数未实现会编译失败，实施时需确认
- **"清空数据"按钮遍历机制**（审查修复 Y4）：复用 #4 新增的 `VisualizationArea::activeChannels()` 拿到通道列表，逐个 `visualizer(mi, ci)->clearData()`。不新增接口，`activeChannels()` 一法多用。按钮实现：`for (auto ch : visArea->activeChannels()) visArea->visualizer(ch.first, ch.second)->clearData();`
- **Ribbon 集成机制**（审查修复 #11）：实施时参照现有 ribbon 运行按钮（运行/暂停/停止）的添加方式，用相同机制加"清空数据"按钮，设计文档不预先定死
- **可视化组件空闲态纳入本次交付**（审查修复 #12）：用户勾选后看到空白面板会困惑，体验断档。组件无数据时 paintEvent 画"等待数据"占位文本，实现简单

### 🔴 已知问题：切换项目未重置运行页状态

当前 `onProjectClosed()` 调用 `destroyEngine()` 销毁引擎，但：

- `ExecutionDashboard` 实例可能仍然存活（central_stack 中的 widget 不自动销毁）
- SignalTreePanel 中的树数据和勾选状态未清空
- VisualizationArea 中的可视化组件和采样数据未清空
- 重新打开另一个项目再切到运行页，旧项目的监听器树和数据可能残留，导致 UI 状态错误

**决策（已采纳）**：方案 A — `onProjectClosed()` 中显式清理

**做法**：
- **仅在 `onProjectClosed()` 中添加**清理步骤（不得放入 `destroyEngine()`，否则 `runNextInQueue` 每次销毁引擎会清空可视化组件，破坏决策 3 的常驻设计）：
  - 清空 SignalTreePanel 树结构和勾选状态
  - 销毁 VisualizationArea 中的所有可视化组件
  - `topo_mtimes_.clear()` 清空时间戳缓存（审查修复 Y3，虽用绝对路径做 key 跨项目不会误命中，但既声明就落实）
- 不清除 `ExecutionDashboard` 本身（不重建，减少开销）

**理由**：
- `onProjectClosed()` 已包含 `destroyEngine()` + 清理 SignalRegistry，语义一致——关闭项目即清除其 UI 状态
- 与决策 1 不冲突：下次打开项目切到运行页，`setDashboard()` 重新 `syncProjectTopologies()` + `refreshMonitorTree()`，数据自然恢复
- 比重建整个 Dashboard 成本低，不影响信号连接

## 开发计划

### 开发模型选型

采用**混合模型：纯逻辑 TDD + UI/串联 增量**（与 `my_ideas.md` 开发模型选型一致，参照日志筛选功能验证过的方式）。

| 类型                      | 改动点                                                                                  | 模型 |
| ------------------------- | --------------------------------------------------------------------------------------- | ---- |
| 纯逻辑、输入输出明确      | `MonitorManager` 拆 clear、mtime 比较、`activeChannels()`、`setMonitorTree(preChecked)` | TDD  |
| UI / 生命周期串联、难单测 | Ribbon 按钮、空闲态、onProjectOpened/Closed 串联、runNextInQueue 恢复                   | 增量 |

**不一次做完**：14+ 改动点横跨 engine/app 多模块，有依赖链。一次做完中间出错难定位、难回退。分阶段每步能编译跑通，符合 CLAUDE.md "每步 subagent 审查 + 手动验证"。

### 阶段划分（增量交付，底层到上层）

每阶段可独立编译验证、可回退，阶段间有依赖按序执行。每阶段完成后派 subagent 代码审查。

#### 阶段 1 - MonitorManager 拆 clear（TDD）

- `clear()` -> `clearRuntime()`（清 buffer_）+ `clearStructure()`（清 tree_cache_ + lookup_table_ + subscribers_）
- 新增两个方法的单元测试（清 buffer 后 tree_cache_/subscribers_ 不变；清结构后 buffer_ 不变）
- 删除 `clear()`（问题根因，唯一调用方 clearTopologyState 将在阶段 2 改造）
- 交付物：`tests/engine/monitor_manager_test.cpp` 绿 + 编译通过

#### 阶段 2 - clearTopologyState 改实现 + syncProjectTopologies 改造（TDD + 增量）

- `clearTopologyState()` 内部改为调 `clearStructure()` + `clearRuntime()`（保留 hw_manager/topology_doc_ 职责）

- 交付物：mtime 比较逻辑单测 + 编译通过

#### 阶段 3 - 新增接口（TDD）
