# 帧协议解析交互问题

## 问题描述

`ProjectStructureWidget`/`ProjectManager` 对协议的管理与 `icd_utility` 的帧协议模型存在割裂，两者各自维护一套逻辑，缺乏统一的领域桥接。

## 割裂点分析

### 1. 两个侧边栏页面功能重叠

| | ProjectStructureWidget (项目概览页) | ProtocolManagerWidget (协议页) |
|---|---|---|
| 列出协议文件 | 扁平文件列表 | 文件+帧层级 |
| 打开编辑器 | double-click | double-click |
| 新建协议 | 空文件 | 带 JSON 模板 |
| 导入 XML | 不支持 | 支持 |
| 重命名/删除 | 支持 | 支持（重复实现） |

用户需要在两个页面间切换做同一类事情，且删除/重命名逻辑各写了一套。

### 2. ProtocolRef 是领域盲的

`ProtocolRef`（`src/core/project/ProjectInfo.h:26`）只有 `{id, name, filePath}`，不携带任何 `icd::Frame`/`icd::Node` 信息。项目层不知道一个协议文件里有哪些帧、哪些信号，每次需要时都得临时解析。

### 3. 没有 project-level Repository 概念

`icd_utility` 的 `Repository` 设计是多帧集合（`ICDConfig.xml` → 多个 `ICDData.xml` → 一个 Repository），但项目层把每个 `.eproto` 当独立文件处理，没有一个"项目协议仓库"来统一查询"这个项目有哪些帧/信号可用"。

### 4. 重复解析逻辑

`ProtocolManagerWidget::parseEprotoFrames()`（`src/app/ProtocolManagerWidget.cpp:417`）手动用 QJsonDocument 解析 `.eproto`，而 `icd_utility` 的 `json_parser` 已经能做同样的事，且输出更完整的 `Repository` 模型。

### 5. 导入是一次性的、无追踪

XML → `.eproto` 转换后，原始 XML 的关系就丢失了。源文件改了无法同步，也没有"这个 .eproto 是从哪个 ICDConfig.xml 导入的"的记录。

## 涉及的关键文件

| 文件 | 角色 |
|------|------|
| `src/app/ProjectStructureWidget.{h,cpp}` | 项目概览侧边栏，通用文件树 |
| `src/app/ProtocolManagerWidget.{h,cpp}` | 协议管理侧边栏，协议专用管理 |
| `src/core/project/ProjectInfo.{h,cpp}` | 项目数据模型，含 `ProtocolRef` |
| `src/core/project/ProjectManager.{h,cpp}` | 项目管理器，含 `registerProtocolRef`/`removeProtocolRef` |
| `src/protocol/ProtocolEditorWidget.{h,cpp}` | 协议编辑器，独立加载 `.eproto` 到 `icd::Repository` |
| `src/icd_utility/include/icd/loader.hpp` | `Loader::init()` 统一加载入口 |
| `src/icd_utility/include/icd/repository.hpp` | `Repository` 多帧容器 |
| `src/icd_utility/src/format/json_parser.hpp` | JSON 解析器，可替代手动解析 |
| `src/icd_utility/src/format/json_serializer.hpp` | JSON 序列化器，`.eproto` 格式写入 |

## 可能的改进方向（待讨论）

### 方向 A：统一到项目树

合并 `ProtocolManagerWidget` 的能力到 `ProjectStructureWidget`，让项目树对 `.eproto` 文件有领域感知（展开显示帧/节点），取消独立的协议页。

### 方向 B：引入 ProtocolService

在 core 层引入协议服务，管理项目级 Repository（加载/缓存/查询所有 `.eproto` 的帧/信号），`ProtocolManagerWidget` 和 `ProjectStructureWidget` 都依赖它。

### 方向 C：两者都做

先引入 ProtocolService 统一数据源，再合并 UI 到项目树。
