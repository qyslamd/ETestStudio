# 设计讨论：架构梳理

一次关于整体架构的讨论记录，梳理了当前对分层、数据流、各层职责的思考。**不代表最终设计**，后续可能根据实际情况调整。

---

## 一、五层架构（当前思路）

```
┌─────────────────────────────────────────────────┐
│                   应用层 (UI)                     │
│  设备管理器 | ICD编辑器 | 用例编辑器 | 监控面板     │
├─────────────────────────────────────────────────┤
│                 测试引擎层 (Engine)                │
│  用例调度 | Lua虚拟机 | 断言/验证 | 报告生成       │
│  API: SetDevice / VerifyDevice / InjectFault     │
├─────────────────────────────────────────────────┤
│               ICD信号层 (ICD)                     │
│  信号路由(工程值↔通道映射) | 协议转换(pack/unpack) │
│  故障注入(FaultManager) | SignalValue转换         │
├─────────────────────────────────────────────────┤
│                   数据池 (DataPool)                │
│  原始字节通道(Pub/Sub): 原始字节 + 元数据         │
│  SignalValue通道(Pub/Sub): 工程值 + 时间戳 + 质量  │
├─────────────────────────────────────────────────┤
│              硬件抽象层 (HAL)                     │
│  设备插件(按类型特化): AD/DA/CAN/1553B/A429/串口  │
│  虚拟设备(Simulate模式) | 厂商SDK封装             │
└─────────────────────────────────────────────────┘
```

### 层间依赖思路

- 上层调用下层接口，下层不反向依赖上层
- 层间通过接口通信
- ICD 和 Engine 不感知数据池——ICD 读写数据池通过内部封装，Engine 不碰数据池

## 二、数据流

### 写路径（Engine → 硬件）

```
Lua: SetDevice("温度", 37.5)
         │
         ▼
Engine --ICD.Set("温度", 37.5)──▶ ICD(查映射→查故障注入→协议封包→SignalValue)
                                       │
                                       ├──▶ 数据池.原始字节通道.Publish(原始字节 + 元数据)
                                       │        │
                                       │        ▼
                                       │    HAL.Subscribe() → 发硬件
                                       │
                                       └──▶ 数据池.SignalValue通道.Publish(工程值+时间戳+质量)
                                                │
                                                ▼
                                            UI 监控订阅
```

### 读路径（硬件 → Engine）

```
HAL(收硬件) --Pub──▶ 数据池.原始字节通道(原始字节 + 元数据)
                          │
                          ▼
                    ICD.Subscribe() → 解协议 → SignalValue
                          │
                          ├──▶ 数据池.SignalValue通道.Publish(工程值+时间戳+质量)
                          │        │
                          │        ├──▶ UI 监控订阅
                          │        └──▶ Engine.Get() 快速读取最新值
                          │
                          └──▶ ICD内部CVT缓存(供下次Get直接返回)
```

### 信号数据结构（草案）

**原始字节元数据**
```cpp
struct RawData {
    QString deviceId;       // 设备唯一ID
    QString channelId;      // 通道ID
    QByteArray data;        // 原始字节
    qint64 timestamp;       // 采集/收发时间(微秒)
    QString protocolId;     // 关联协议ID(ICD层填入)
};
```

**SignalValue**
```cpp
struct SignalValue {
    QString signalId;       // 信号唯一ID
    QVariant value;         // 工程值
    qint64 timestamp;       // 微秒级时间戳
    bool isValid;           // 有效性
    int quality;            // 数据质量(0=正常, 1=可疑, 2=无效, 3=模拟)
    QString sourceInfo;     // 来源描述(设备/通道/协议等)
};
```

## 三、Dry Run（影子运行）

### 思路

```
Engine ──ICD API──▶ ICD ──▶ 数据池 ──▶ HAL(Simulate模式: 虚拟设备生成数据)
                       │                      │
                       ◀──────────────────────┘
```

- Engine 和 ICD 在 Dry Run 模式下无感知
- HAL 层每个插件提供 `simulate()` 模式，切到虚拟数据源
- 数据池不变，数据来源从真实硬件换成虚拟设备
- UI 监控面板无感知，正常订阅 SignalValue 通道

### 可能的触发方式

- 全局开关：整个系统进入 Dry Run，所有设备走虚拟
- 单设备开关：部分设备真实、部分设备虚拟（混合模式）
- 开关位置：HAL 层插件级别，不向上透传

## 四、故障注入

### 在用例层面控制（初步想法）

```
Engine --ICD.InjectFault(signalId, FaultConfig)──▶ ICD内部FaultManager
                                                       │
                                                       ▼
                                               影响ICD转换过程:
                                               - 信号值超限/死滞/固定值
                                               - CRC/校验错误
                                               - 协议字段篡改
                                               - 延迟/丢包(委托数据池)
```

### 故障类型

| 类型 | 实现位置 | 说明 |
|------|---------|------|
| 信号值死滞(Stuck-at) | ICD 转换 | 温度固定读 999 |
| 信号值加偏置/噪声 | ICD 转换 | AD 值多加 5% |
| 协议 CRC 错误 | ICD 封包 | CAN 帧 CRC 字段写反 |
| 校验位错误 | ICD 封包 | 429 label 校验位取反 |
| 通信延迟 | 数据池 | 数据延迟 N ms 到达 |
| 通信丢包 | 数据池 | 按概率丢弃原始字节 |
| 采样率异常 | 数据池 | 数据频率突然变化 |

### 清除

- `ICD.ClearFault(signalId)` — 清除单信号故障
- `ICD.ClearAllFaults()` — 清除所有故障
- 用例结束时自动清除所有活跃故障（待确认）

## 五、ICD 层职责

### 双重角色（讨论中形成的看法）

1. **信号路由（Signal Routing）**
   - 管理"信号名 → 设备ID + 通道ID + 协议ID"的映射关系
   - 管理"信号名 → 转换规则"的映射（线性/多项式/枚举/脚本）
   - SignalValue 总线发布/订阅（供 UI 消费）

2. **协议转换（Protocol Conversion）**
   - pack：工程值 → 原始字节（按协议定义封包）
   - unpack：原始字节 → 工程值（按协议定义解包）
   - 字节序处理（每字段独立配置大端/小端）
   - 协议校验（CRC/和校验/异或）

### ICD 内部结构（草案）

```
ICD Manager
├── SignalMapper          // 信号路由: signalId → deviceId + channelId + protocolId
│   └── 转换规则(线性/多项式/枚举/脚本)
├── ProtocolRegistry      // 协议定义仓库
│   └── Protocol{字段列表 + 字节序 + 校验 + pack/unpack}
├── FaultManager          // 故障注入管理
│   └── 活跃故障列表 {signalId, type, params, active}
├── SignalValueCache      // CVT: 信号最新值缓存(供Engine.Get快速读取)
└── DataPoolAdapter       // 数据池读写封装(上层无感知)
```

## 六、HAL 插件设计原则

### 按类型特化，不追求万能接口（个人倾向）

```
IDevicePlugin(基类: 生命周期+元数据)
├── ISerialPlugin          // 串口族: RS232/422/485
│   ├── BaudRate/DataBits/Parity/StopBits 配置
│   └── asyncWrite/dataReceived
├── ICanPlugin             // CAN/CAN FD
│   ├── BitRate/IDFilter/Mode 配置
│   ├── sendFrame(标准帧/扩展帧)
│   └── frameReceived
├── IARINC429Plugin        // A429
│   ├── Label/SDI/SSM/BitRate 配置
│   ├── sendLabel()
│   └── labelReceived
├── IMil1553Plugin         // 1553B: BC/RT/MT
│   ├── Mode 配置(BC/RT/MT)
│   ├── bcSchedule/Msg
│   └── rtResponse/mtMonitor
├── IADevicePlugin         // 模拟量采集
│   ├── Channels/SampleRate/Range/Trigger 配置
│   ├── start采集/stop采集
│   └── dataReady(多通道数据)
├── IDADevicePlugin        // 模拟量输出
│   ├── Channels/Range 配置
│   └── setOutput(channel, value)
├── IDioPlugin             // 开关量IO
│   ├── 通道方向配置(输入/输出)
│   ├── readInput(channel)
│   └── setOutput(channel, value)
├── ITcpPlugin             // TCP(走标准Qt)
│   ├── 模式(client/server)
│   ├── asyncWrite/dataReceived
│   └── clientConnected/disconnected
```

### 所有插件额外能力

- `simulate(bool enable)` — 切换到虚拟数据源
- `selfTest()` — 自检
- `deviceStatus()` — 当前状态(在线/离线/异常/模拟)
- `configMetaData()` — 配置参数元数据（可用于自动生成配置界面）

## 七、Engine 层设计思路

### 与 ICD 的交互方式

Engine **不直接操作数据池**，所有硬件/信号操作通过 ICD API（待定型）：

```cpp
class IICDEngineInterface {
    virtual bool setSignal(const QString &signalId, const QVariant &value, QString *err = nullptr) = 0;
    virtual SignalValue getSignal(const QString &signalId, bool *ok = nullptr) = 0;
    virtual bool verifySignal(const QString &signalId, const QVariant &expected,
                              const Tolerance &tolerance, QString *err = nullptr) = 0;
    virtual bool injectFault(const QString &signalId, const FaultConfig &fault, QString *err = nullptr) = 0;
    virtual void clearFault(const QString &signalId) = 0;
    virtual void clearAllFaults() = 0;
};
```

### Lua API 风格（初步设想）

```lua
SetDevice("温度", 37.5)
VerifyDevice("温度", 37.5, {min=-0.1, max=0.1})
InjectFault("温度", {type="stuck_at", value=999})
Delay(1000)
```
