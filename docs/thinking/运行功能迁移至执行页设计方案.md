# 运行功能迁移至执行页设计方案

> 范围：将运行相关功能（程序选择、验证、运行、运行全部、验证结果）从 page0 迁移到 page1（执行仪表盘），ribbon 按 page 切换内容。
>
> 状态：设计文档，待评审。评审通过后再实施。
>
> 关联文档：`运行相关UI操作问题分析.md`（该文档分析的问题暂缓，本方案不直接处理，但方向一致）。

## 1. 背景与目标

### 1.1 现状问题

当前运行操作链路跨两个互斥全屏页面，割裂感强：

1. 用户在 page0 sidebar 勾选程序；
2. 在 ribbon 点「验证」，结果出在 page0 底部 ProblemsPanel；
3. 在 ribbon 点「运行」/「运行全部」，`run()` 末尾 `central_stack_->setCurrentIndex(1)` 自动跳到 page1；
4. page1 看监控，但 page0 的勾选状态、验证结果都看不到了；
5. 想改勾选或回头核对，得切回 page0，而 page0 又看不到运行状态。

根因：操作对象（程序选择）在 page0，操作结果（监控）在 page1，两者互斥全屏切换。

### 1.2 目标

把"运行"从 ribbon 的一个动作，升级成 page1 这个"执行视图/工作模式"。page1 自闭环完成：选程序 -> 验证 -> 运行 -> 看监控。page0 回归纯编辑。

### 1.3 设计决策（已与用户确认）

| 决策点 | 结论 |
|---|---|
| TestProgramManagerWidget | 拆分：page0 留文件管理（新建/删除/重命名/双击打开），去掉勾选；page1 通过 ribbon 选择运行目标 |
| activity bar | page1 不要；page1 靠 ribbon category tab 切回 page0 |
| page1 布局 | 三列 + 底部输出保持不变；程序选择放 ribbon；验证结果放 page1 底部输出，做可点击链接跳转回 page0 |
| ribbon | 按 page 切换内容：page0 显示编辑相关 category，page1 显示执行相关 category，公共 category 两边都显示 |
| QAB mode_toggle_action_ | 删除。category tab 作为唯一切页入口；原 mode_toggle 的副作用（disableEditActions/enableEditActions、ribbonBar objectName 指示线）迁移到 category 切换逻辑 |

## 2. 总体设计

### 2.1 页面模型

```
central_stack_ (QStackedWidget)
├── page 0  page_editor_widget_   编辑态（不变）
│   ├── ActivityBarWidget
│   └── h_splitter_
│       ├── SidebarWidget  ← TestProgramManagerWidget（仅文件管理，无勾选）
│       ├── v_splitter_
│       │   ├── EditorArea (DockManager)
│       │   └── BottomContainerWidget  ← 日志/输出/问题/终端（编辑态用）
│       └── AuxSidebar
└── page 1  exec_dashboard_page_  执行态
    └── 三列：ExecutionDebugWidget | SignalTreePanel | VisualizationArea
        + 底部输出（新增"问题"tab，与"输出"tab 并列）
```

page1 不加 activity bar，不重新引入 sidebar。程序选择、验证、运行全部通过 ribbon 完成。

### 2.2 ribbon category 划分

ribbon category 分为三组，所有 tab 始终可见，通过点击 tab 切换 central_stack page：

| 分组 | category | 点 tab 切换行为 |
|---|---|---|
| 编辑组 | 主页（含文件/编辑 panel）、视图 | 切换到 page0（编辑态） |
| 执行组 | 执行 | 切换到 page1（执行态） |
| 公共组 | 工具、帮助 | 不切页（始终在当前页） |

> 现状代码（`MainWindow.cpp:2080` 起）共 5 个 category：主页、视图、运行、工具、帮助。「文件」「编辑」是「主页」category 下的两个 panel，**不是独立 category**，上表"主页（含文件/编辑 panel）"即指此。「帮助」category（`MainWindow.cpp:2276`，含"关于"panel）归公共组--"关于"是全局信息，与页面无关，两边可见，与「工具」一致。
>
> 注：`hideCategory`/`showCategory` 会将 category tab 从 tab bar 移除/添加，导致用户无法点击隐藏的 tab 来切换页面。故不采用显隐方案，所有 tab 始终可见，仅通过 `currentRibbonTabChanged` 信号绑定中央堆叠页切换。

「执行」category 是新建的，整合原「运行」category 的内容，并新增「程序选择」panel。原「运行」category 删除。

「视图」category 现有的面板显隐 action（日志/问题/终端/辅助侧边栏）作用于 page0 的 BottomContainerWidget 和辅助侧边栏，归 page0 专属，不随 page1 显示。

**删除 `view_execution_output_action_`**（`MainWindow.cpp:2141`）。它控制 `execution_output_panel_->setVisible()`，但该面板已注入 page1，不在 page0 `bottom_container_` 内，从 page0 点击看不到效果。迁移后 page1 输出面板是 `bottom_tabs_` 的一个 tab，tab 自带关闭按钮控制可见性，action 冗余。其余 view action 保留（日志/终端控制 page0 面板，有效；`view_problems_action_` 去留见 6.1）。

## 3. 详细设计

### 3.1 ribbon category 与 central_stack 双向绑定

**前提：删除 QAB `mode_toggle_action_`**。现状中 QAB 的 `mode_toggle_action_`（`MainWindow.cpp:1958`）是一个独立的 page 切换入口，与 `central_stack_::currentChanged` lambda（`MainWindow.cpp:1118`）双向同步。新方案引入 category<->stack 绑定后会有三个控制源（QAB action、category tab、currentChanged）争抢 page 状态。为避免多源协调复杂度，删除 `mode_toggle_action_`，category tab 作为**唯一**切页入口。

原 `mode_toggle_action_` 的副作用迁移到 category 切换逻辑（currentChanged lambda）：

- `disableEditActions()` / `enableEditActions()`：**保留**。这两个函数 disable/enable「主页」category 里文件 panel 和编辑 panel 的 action（save/undo/cut 等），而这些 action 绑了快捷键且 `save_action_->setShortcutContext(Qt::ApplicationShortcut)`（`MainWindow.cpp:1865`）等，ApplicationShortcut 在整个应用窗口范围生效，不局限于 action 可见的 widget。即使「主页」category 在 page1 隐藏，Ctrl+S/Ctrl+Z/Ctrl+X 等快捷键在 page1 仍会触发对应 action。若不 disable，用户在执行态按 Ctrl+S 会触发隐藏编辑器的保存、Ctrl+Z 触发撤销，造成混乱。故函数必须保留，触发点从原 mode_toggle triggered lambda 迁移到 `central_stack_::currentChanged` lambda：page0->page1 调 disableEditActions，page1->page0 调 enableEditActions。函数本身不动，保持独立可复用（与原 mode_toggle 调用方式一致，仅换触发源）；
- `ribbonBar()->setObjectName("RunningMode")`：page1 时设，page0 清空，用于 QSS 画 ribbon 底部指示线，保留。

**绑定规则**：

- 点「执行」category tab -> `central_stack_->setCurrentIndex(1)`；
- 点编辑组任一 category tab -> `central_stack_->setCurrentIndex(0)`；
- 点公共组（工具/帮助）category tab -> 不切页；
- `central_stack_` currentChanged -> raise 对应 category tab，同步选中状态。

**信号环避免**：category 切换触发 page 切换，page 切换又会触发 category raise，可能成环。用一个 `bool switching_page_` 守卫标志，在程序化切换时置位，信号回调里判断该标志跳过。删除 `mode_toggle_action_` 后控制源减为一个（category tab），环路径简化为 category<->stack 两端，守卫逻辑更易覆盖。

**守卫粒度**：守卫**只跳过会触发环的 category raise 部分**，`disableEditActions`/`enableEditActions`、`ribbonBar()` objectName 等副作用始终执行，不受守卫影响。否则程序化切页时守卫整体跳过 lambda，会导致编辑 action 状态不刷新。

> 不采用 `hideCategory`/`showCategory`：这些 API 会将 category tab 从 tab bar 中移除，导致用户无法点击隐藏的 tab 来切换页面。所有 tab 始终可见，绑定只做 page 切换 + tab 同步 raise。

**SARibbon API**（已确认，SARibbon 2.5.7）：

- 显隐 category：`ribbonBar()->hideCategory(SARibbonCategory* cat)` / `showCategory(SARibbonCategory* cat)`（**注意**：hideCategory 会把 tab 从 tab bar 移除，不适用于 page 切换场景。所有 tab 始终可见，不使用此 API）；
- 监听 category 切换：`SARibbonBar::currentRibbonTabChanged(int index)` 信号；
- 主动 raise：`ribbonBar()->setCurrentIndex(int index)` 或 `ribbonBar()->raiseCategory(SARibbonCategory* cat)`；
- 按索引取 category：`ribbonBar()->categoryByIndex(int index)`，反向 `categoryIndex(const SARibbonCategory*)`；
- 删除 category：`ribbonBar()->removeCategory(SARibbonCategory* cat)`。

### 3.2 程序选择（ribbon popup）

在「执行」category 新增「程序选择」panel，放一个「程序选择」按钮（QToolButton + popup）。

**popup 内容**：带 checkbox 的程序列表（多选），数据源复用项目 `cases/` 目录的 `.etprog` 扫描（与 page0 的 TestProgramManagerWidget 同源）。

**动作语义（重新定义）**：

| 动作 | 目标来源 | 说明 |
|---|---|---|
| 运行 | popup 选中集合 | 1 个或多个，多个串行；空则禁用 |
| 全部运行 | 项目 `.etprog` 全集 | 扫全集顺序跑，与选中状态无关，不退化 |
| 验证 | 选中非空时校验选中集合，为空时校验全集 | 与下方 enable 规则配合，对两种运行模式都可用 |

选择只服务于「运行」，「全部运行」自成动作不依赖选择。popup 内只有一个多选集合，无双状态歧义。

**与编辑器的关系**：编辑器是否打开测试程序，与运行无关。运行目标完全由 popup 选择决定，编辑器纯粹是编辑工具。`checkCanRun` / `checkCanVerify` 中对 `TestProgramEditorWidget` 的判定可去掉（呼应问题分析文档"统一运行目标解析"方向）。

**运行内容来源（统一磁盘加载 + 未保存提示）**：

`run()` / `runAll()` / `runNextInQueue()` 中**程序内容**统一用 `loadTestProgram(path)` 从磁盘加载（**拓扑加载 `loadProjectTopologies()` 逻辑暂不动**，独立问题另案处理）。删除现状 `run()` 里整个编辑器分支（`ExecutionPanelController.cpp:429-433`），包括 `editor->save()` 隐式保存和 `prog_editor->programData()` 内存读取。删除 `runAll()` 的两个退化分支：`if (prog_editor) { run(); return; }`（624-631）和 `if (paths.size() < 2) { run(); return; }`（639-643），`runAll()` 一律走 `runNextInQueue` 队列。编辑器内存不参与运行，与"编辑器与运行无关"基调一致。

`run()` 选中 ≥2 个程序时填 `run_queue_` 调 `runNextInQueue()`，选中 1 个时直接执行（保留现有单次执行流程：load → createEngine → loadTopologies → start）。`run()` 本身不再直接调 `engine_->start()`（≥2 时由 `runNextInQueue()` 启动），选中 1 时保留直接启动路径。

为避免用户跑了编辑器中未保存的旧版而不自知，运行前检测未保存并提示：

- 队列启动时（`run` 单次、`runAll` 全集）一次性扫描目标程序集合，找出在编辑器打开且 `isModified()` 的文件；`runNextInQueue` 是队列推进函数（每跑完一个调一次），**不触发扫描**，避免"中途逐项不再弹"被违反；
- 若存在未保存目标，弹模态确认框「运行前保存」：列出未保存文件清单，三按钮：
  - **保存并运行**：逐个 `editor->save()` 后加载磁盘内容运行；任一 save 失败则提示并中止整个运行；
  - **不保存运行**：直接 `loadTestProgram(path)` 跑磁盘当前内容（给用户跑稳定旧版的出口）；
  - **取消**：中止，不运行；
- 无未保存目标：静默运行，不弹框；
- 该提示逻辑封装在 `ExecutionPanelController` 内，由 run/runAll 共用（runNextInQueue 不触发扫描，见上）。

**enable / 验证规则**：

- 验证 enable：仅要求项目已打开（`verify()` 会自行发现并报告 ICD/拓扑/程序等缺失项，不在 enable 门限重复拦截）；
- 验证目标：选中非空校验选中集合，选中为空校验全集（等价于"全部运行"的前置检查）；
- 运行 enable：选中集合非空；
- 全部运行 enable：项目有 `.etprog`。

**verify() 第 5 项「测试程序可用」改造（方案 A）**：

现状（`ExecutionPanelController.cpp:562-586`）按"编辑器/勾选/选中"判定，改造为按目标集合统一判定：

- 取目标集合：选中非空用选中集合，否则用全集（`.etprog` 全扫）；
- 遍历每个 `.etprog` 用 `loadTestProgram` 查 `cases` 是否非空；
- **任一文件 cases 非空 -> `has_program = true`，通过**（集合里至少有一个能跑即满足运行语义）；
- 全部为空 -> 报错，NavTarget::Program，描述"无可用测试程序"（涵盖"选中集合全空"和"全集全空"两种场景，字面不再误导）；
- 去掉原编辑器/勾选/选中的判定分支。

> 选 A 而非"逐个都有用例才过"（B）：运行对空用例文件的实际行为是跳过/单文件报错，不会让整个运行失败；验证比运行更严会让用户困惑"验证说不行但运行能跑（跳过空的）"。

**`updateRunControls` 定义**：仅更新 run/runAll 的 enable 状态（不重算 verify），用于 popup 选中变化和项目打开/关闭等不影响验证状态的场景。`updateRunControls` 不调 `syncControlStates`，直接调 `checkCanRun()`/`checkCanRunAll()` 设 `act_run_`/`act_run_all_`。`syncControlStates` 全量刷 5 个 action（含 verify/pause/stop），在引擎状态变化或项目切换时调用。

**按钮摘要**：「已选 N 个」/「未选」。「全部运行」无需摘要（与选择无关）。

**数据流**：popup 维护 `selected_paths_` 单一状态。`ExecutionPanelController` 的 `run()` / `runAll()` / `verify()` 改为从 popup 读取目标，不再从 `TestProgramManagerWidget` 或编辑器读。`TestProgramManagerWidget` 去掉 `checkedProgramPaths()` 等勾选相关接口。

**popup 接口与 ownership**：

`ProgramSelectionPopup` 是纯 UI 组件（QToolButton + popup QWidget，内含 checkbox 多选列表），由 `ExecutionPanelController` 构造并持有，MainWindow 通过 getter 取出放入 ribbon。与现有 `act_run_` / `act_verify_` 等 QAction 模式一致（Controller 创建、MainWindow 放置）。

```cpp
class ProgramSelectionPopup : public QWidget {
  Q_OBJECT
public:
  QStringList selectedPaths() const;    // 当前选中集合
  bool hasAnyProgram() const;           // 全集非空（供验证/全部运行 enable）
  int selectedCount() const;            // 摘要用（"已选 N 个"）
  void refreshList();                   // 重扫 cases/*.etprog
signals:
  void selectionChanged();              // 驱动 updateRunControls
};
```

`ExecutionPanelController` 新增 `setProgramPopup(ProgramSelectionPopup* popup)` setter（MainWindow 在 lazyInit 中调用），存储 `popup_` 成员。`checkCanRun()` 第 3 项改为 `!popup_->selectedPaths().isEmpty()`，`checkCanVerify()` 第 4 项改为 `popup_->hasAnyProgram()`（去掉编辑器分支和 `test_program_mgr_` 依赖），`checkCanRunAll()` 新增：预条件 + canRun + `popup_->hasAnyProgram()`。

### 3.3 page1 底部输出：新增「问题」tab

**现状**：page1 底部是单一 `ExecutionOutputPanel`（运行日志），由 `ExecutionDashboard::setOutputPanel` 注入。

**改造**：page1 底部改为 `QTabWidget`，两个 tab：

| tab | 内容 | 数据来源 |
|---|---|---|
| 输出 | 运行日志（现有 ExecutionOutputPanel） | TestExecutionEngine 信号 |
| 问题 | 验证结果清单（结构化表格） | verify() 生成 |

「问题」tab 复用 page0 的 `ProblemsPanel` 组件（QTableWidget，4 列：文件/行/描述/类型），但**独立实例**，不与 page0 的 ProblemsPanel 共享。page0 的 ProblemsPanel 去留见 6.1。

**接口方案（B：ExecutionDashboard 内部创建 ProblemsPanel）**：

ProblemsPanel 是执行视图的组成部分，与 SignalTreePanel、ExecutionDebugWidget 同属 ExecutionDashboard 内部子组件，其 ownership 归 ExecutionDashboard。外部不持有指针。

`ExecutionDashboard` 改动：

- `initUi` 中，`vert_splitter_` 第二格从直接放 `output_panel_` 改为放 `QTabWidget`（`bottom_tabs_`）；
- 「输出」tab：`setOutputPanel` 被调用时，把注入的 output_panel 放入「输出」tab；
- 「问题」tab：`initUi` 时内部 `new ProblemsPanel` 放入「问题」tab，由 ExecutionDashboard 持有 `problems_panel_`；
- 新增 `ExecutionDashboard::problemsPanel()` getter；
- `setOutputPanel` 接口签名不变，保持向后兼容。

`ExecutionPanelController` 访问路径：通过已注入的 `dashboard_->problemsPanel()` 取问题面板，写问题项、连点击信号都走这里。

**postInit 参数清理**：

controller 改用 `dashboard_->problemsPanel()` 和 `popup_->selectedPaths()` 后，原 postInit 注入的 `problems_panel_`、`bottom_container_`、`test_program_mgr_` 三个成员变 dead code。按阶段分批移除：

| 参数 | 阶段 | 去留 | 原因 |
|---|---|---|---|
| `test_program_mgr` | 阶段二 | 移除 | 运行目标改由 popup 提供 |
| `problems_panel` | 阶段三 | 移除 | 改用 `dashboard_->problemsPanel()` |
| `bottom_container` | 阶段三 | 移除 | 切问题面板改用 `dashboard_->setCurrentBottomTab()` |
| `editor_mgr` | — | **保留** | 编辑器只读/恢复 + 未保存检测 |
| 其余（`output_panel`/`signal_registry`/`icd_repository`/`status_bar_ctrl`） | — | 保留 | 不变 |

- postInit 签名移除 `test_program_mgr`、`problems_panel`、`bottom_container` 三个参数；
- `ExecutionPanelController` 移除对应的三个成员变量（`test_program_mgr_`、`problems_panel_`、`bottom_container_`）；
- `problems_panel_` 的 4 处引用：122 行（成员初始化）删除，511/514/604 行改写为 `dashboard_->problemsPanel()`；
- MainWindow lazyInit 调用 postInit 处分阶段去掉对应实参（阶段二去 `test_program_mgr_`，阶段三去 `problems_panel_` 和 `bottom_container_`）；

> output_panel 仍由 MainWindow 创建并注入（它是历史遗留的 MainWindow 成员），与 problems_panel 内部创建存在不一致，但这是既有现状，本方案不扩 scope 清理。

**tab 切换时机**：

- 验证完成且有 errors/warnings -> 自动切到「问题」tab；
- 运行启动 -> 自动切到「输出」tab；
- 用户手动点 tab -> 尊重用户选择。

ExecutionDashboard 需暴露 `setCurrentBottomTab(int)` 或类似接口供 ExecutionPanelController 切换；tab 切换的判断逻辑（errors>0、运行启动）仍在 ExecutionPanelController，Dashboard 只提供切 tab 能力。

**verify() 副作用**：`verify()` 末尾两个副作用迁移后自然生效，保留不改：

- `debug_widget_->setDependencies(...)`：刷新 page1 ExecutionDebugWidget 顶部"运行前提"overview 区。迁移后 debug_widget 仍在 page1，生效。overview 区与底部切到哪个 tab 无关，时机无冲突；
- `syncControlStates()`：刷新 ribbon run/runAll enable。迁移后 run/runAll 在 page1「执行」category，生效。

### 3.4 验证结果项的可点击跳转

「问题」tab 的每一行做成可点击，点击后跳回 page0 对应位置。

**跳转目标映射**：

| 验证错误 | NavTarget 枚举 | 跳转目标（page0） |
|---|---|---|
| 未打开项目 | `Project` | 仅提示，不跳转（无目标可跳） |
| ICD 协议未加载 | `Icd` | sidebar 切到「协议」页（ProtocolManagerWidget） |
| 未找到拓扑文件 | `Topology` | sidebar 切到「拓扑」页（TopologyManagerWidget） |
| 拓扑未绑定信号 | `Signal` | sidebar 切到「拓扑」页，由用户自行选择 .etopo（见 6.2） |
| 无可用测试程序 | `Program` | sidebar 切到「测试程序」页（TestProgramManagerWidget），编辑空用例文件 |
| 硬件/Mock 未配置 | `Hardware` | sidebar 切到「硬件」页（HardwareTreeWidget） |

> 「拓扑未绑定信号」的精确定位缺陷见 6.2。

**接口方案（B：controller 发导航信号，MainWindow 接收执行）**：

导航是跨 central_stack / sidebar / editor_manager 三个 MainWindow 资源的连贯动作，逻辑上属于一处。MainWindow 天然拥有全部三个资源，是执行导航的归属地。controller 不持有 `sidebar_`，不直接执行导航，只声明"我要导航到哪个错误来源"。

- 定义 `NavTarget` 枚举：`Project`、`Icd`、`Topology`、`Signal`、`Program`、`Hardware`（对应 verify 的 6 条检查）；
- `ExecutionPanelController` 新增信号 `navigateRequested(NavTarget target, const QString& path)`；
- `ProblemsPanel` 点击信号直接带出 `NavTarget`（见下方列结构方案 A），controller 透传 emit `navigateRequested`，无需 source->NavTarget 转换；
- `ExecutionPanelController` **不注入 `sidebar_`，不为导航功能扩展 postInit 参数**（postInit 的 problems_panel 参数移除见 3.3，导航不再新增参数）；
- `MainWindow` 连接 `navigateRequested` 到槽 `onNavigateToProblem`，槽内持有完整的跳转目标映射（NavTarget -> sidebar 页 ID / 文件），依次执行 `central_stack_->setCurrentIndex(0)` -> 按 target 切 sidebar 页或 openFile -> category 双向绑定自动把 ribbon 切回编辑组。

**职责边界**：

- controller：识别"点击了哪个错误" -> 透传 NavTarget -> 请求导航；不关心具体怎么切。
- MainWindow：拥有 sidebar 页 ID 知识，执行"错误来源 -> UI 位置"的映射与三步动作。

**ProblemsPanel 列结构方案（A）**：

现状 ProblemsPanel 4 列「文件/行/描述/类型」，但「文件」「行」两列 verify() 从未填真实内容（source 全传「运行」），实际只有「描述」「类型」有用。冲突在于：跳转需要 NavTarget 枚举（类型安全），显示列需人类可读名（"ICD 协议"），两者不能塞同一字符串。方案 A 用 Qt::UserRole 分离显示与数据，并简化列结构。

- `ProblemsPanel::addProblem` 签名改为 `(NavTarget target, const QString& displayName, const QString& type, const QString& message)`；
- 列结构简化为 3 列「来源/描述/类型」，删除一直空置的「行」列；
- 列 0「来源」item 的 `Qt::UserRole` 存 NavTarget 值（int），显示文本为 displayName（如「ICD 协议」「拓扑」「测试程序」）；
- 点击信号 `problemActivated(NavTarget)` 直接带枚举；
- verify() 调用形如 `addProblem(NavTarget::Icd, QStringLiteral("ICD 协议"), QStringLiteral("错误"), QStringLiteral("ICD 协议未加载"))`。

> 类型安全：NavTarget 从 verify() 一路传到点击处理，无字符串<->枚举往返转换。displayName 由 verify() 传入（它本就构造描述消息、知道上下文），ProblemsPanel 保持哑视图不持有业务映射。
> 对 page0 ProblemsPanel 的影响：改签名同时影响 page0 实例，但 verify() 是唯一 caller，且 page0 ProblemsPanel 去留见 6.1（倾向移除），可控。

## 6. 待确认与风险

### 6.1 待确认

- **SARibbon category 显隐 API**：实施时确认 `setCategoryVisible` 或等价方法的可用性。若 SARibbon 不支持运行时显隐 category，降级方案为「所有 category 常驻，但 page 切换时禁用无关 category 的 action」。**降级方案下，category tab 的点击切页行为必须保留**（`currentCategoryChanged` 信号独立于 action enable），仅 category 内 action 禁用。若 SARibbon 连 tab 点击也阻断，降级方案不可用，需另寻方案（如保留 category 显隐或引入快捷键兜底）。（注：实施中已确认所有 tab 始终可见即可满足切页需求，未用 hideCategory，降级方案未触发。）
- ~~**page0 的 ProblemsPanel 实例去留**~~：已决--阶段三移除。verify 改走 page1 后 page0 的 ProblemsPanel 成空壳，连同 `view_problems_action_` 和配置项一并清理，page0 底部只留「日志」「终端」。

### 6.2 风险

- **双向绑定的信号环**：守卫标志必须覆盖所有路径，否则会无限递归。需充分测试 category 反复切换、程序化切换与用户切换交替的场景。
- **popup 状态与运行队列的一致性**：popup 的勾选状态在项目切换、文件删除后需主动失效或清理，否则 runAll 会用过期路径。需在 `projectOpened`/`projectClosed` 和文件删除时同步 popup。
- **page1 无 activity bar 的回退路径**：删除 QAB `mode_toggle_action_` 后，page1 回 page0 只能靠 ribbon category tab。需确保「工具」category 始终可见、ribbon tab 始终可点。原方案设想的 Ctrl+0/1 快捷键不再需要（它本是为弥补 QAB 而设）。若后续测试发现 ribbon 绑定有边角失效，可再补一个键盘快捷键作兜底，当前不引入。
- **「视图」category 的面板显隐 action 在 page1 失效**：这些 action 控制 page0 的 BottomContainerWidget，page1 上用户点击看不到效果。category tab 始终可见，但点击后切换到 page0 才会生效（视图 tab 是编辑组，点它会切到 page0），故 page1 上点视图 action 不会产生可见效果，但也不造成危害。**已核查快捷键绕过风险**：`view_output_action_`/`view_problems_action_`/`view_terminal_action_`/`view_aux_sidebar_action_` 创建处（`MainWindow.cpp:2134-2167`）均只 `setCheckable` 未 `setShortcut`，无快捷键触发路径。
- **「拓扑未绑定信号」无法精确定位文件**：`signal_registry_` 由 `loadProjectTopologies()` 累积加载所有 .etopo，verify() 内部无法反查是哪个文件缺信号绑定。3.4 该行的映射已改为"切到拓扑 sidebar 让用户自行选择"，不承诺精确定位，规避此风险。
