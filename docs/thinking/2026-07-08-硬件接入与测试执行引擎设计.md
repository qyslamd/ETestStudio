# 硬件接入与测试执行引擎设计

> **版本**: v1.0
> **日期**: 2026-07-08
> **状态**: 设计阶段

## 1. 概述

本文档描述 ETest 系统中硬件接入层与测试执行引擎的整体架构设计。

### 设计目标

- 定义统一的硬件设备驱动接入标准（延续现有 Plugin 体系）
- 设计测试执行引擎，支持 IDE 调试模式与独立引擎两种运行形态
- ICD 数据参与完整的信号编解码链路，覆盖全部设备类型
- 支持 AD、DA、Serial、CAN、ARINC 429 五种设备类型
- 支持 14 种测试命令（含控制流 LOOP/WHILE/IF）
- 执行结果输出到独立的 `.etlog` JSON 文件
- `.etlog` 命名规则：`.etprog` 文件名去掉后缀，如 `燃油阀门控制.etlog`

### 关键设计决策

| 决策 | 结论 |
|------|------|
| 硬件接入方式 | 真实驱动也走 Plugin 体系（方案 A） |
| 引擎形态 | 进程内库 + 独立 GUI 程序（test-executor） |
| 脚本引擎 | 先用 C++ 顺序执行器 |
| ICD 参与 | 所有设备类型必经 ICD 编解码 |
| 设备实例 | deviceId → IDevicePlugin* 一对一 |
| 线程模型 | Worker QThread，不阻塞 UI |
| 执行超时 | 引擎从 step.timeoutMs 读取超时值，在工作线程侧用定时器监测硬件操作；步骤未设超时时用引擎默认值兜底 |
| 结果文件 | `.etlog` 独立 JSON 格式 |
| 实现阶段 | Phase 1: 引擎核心 + mock 驱动 → Phase 2: 真实驱动 |

         → 执行完毕 → 写入 .etlog → 用户可查看结果后关闭
```

## 3. 组件设计

### 3.1 Signal Resolver（信号解析器）

**职责**：将测试步骤中的 UUID 解析为引擎可执行的信号描述。

```
Input:  UUID (32 hex chars)
  ↓
① 查 SignalRegistry::resolve(uuid) → ResolvedSignalData
  ↓
② 查 ICD Repository 补充完整元数据
Output: ResolvedSignal
```

**核心数据结构**：

```cpp
struct ResolvedSignal {
  // ── 设备身份 ──
  QString deviceId;
  QString portName;

  // ── 信号类型（决定了编解码方式和硬件操作接口） ──
  SignalType signalType;  // AD | DA | CAN | SERIAL | A429

  // ── 工程值映射（所有类型通用） ──
  double coeff;     // 转换系数
  double offset;    // 转换偏移量
  QString unit;     // 工程单位（℃, V, rpm, ...）
  double engMin;    // 工程值范围下限
  double engMax;    // 工程值范围上限
  double rawMin;    // 原始值范围下限
  double rawMax;    // 原始值范围上限

  // ── 通道型设备（AD/DA） ──
  int channel;      // 物理通道号

  // ── 帧型设备（CAN/Serial/A429） ──
  uint32_t frameId;     // CAN ID / A429 Label
  int byteOffset;       // 帧内字节偏移
  int bitOffset;        // 位偏移
  int bitWidth;         // 位宽
  ByteOrder byteOrder;  // BigEndian / LittleEndian

  // ── 超时配置（从步骤参数注入） ──
  int timeoutMs = 30000;  // 默认 30s

  // ── resolve 失败标记 ──
  bool valid = false;    // resolve() 设为 true，解析失败保持 false
};
```

### 3.2 Signal Codec（信号编解码器）

**职责**：工程值与原始值/原始字节之间的双向转换。

```cpp
class SignalCodec {
 public:
  // 写路径：工程值 → 原始值（AD/DA）或 帧字节（CAN/Serial/A429）
  QVariant encode(double engValue, const ResolvedSignal& info);
  QByteArray encodeToFrame(double engValue, const ResolvedSignal& info);

  // 读路径：原始值（AD/DA）或 帧字节（CAN/Serial/A429） → 工程值
  double decode(const QVariant& rawValue, const ResolvedSignal& info);
  double decodeFromFrame(const QByteArray& frameData,
                         const ResolvedSignal& info);

 private:
  // 线性映射：eng = raw × coeff + offset
  double linearMap(double raw, const ResolvedSignal& info);
  double inverseLinearMap(double eng, const ResolvedSignal& info);

  // 帧型设备的位打包/解包
  QByteArray packBits(double value, const ResolvedSignal& info);
  double unpackBits(const QByteArray& data, const ResolvedSignal& info);
};
```

编解码逻辑因设备类型而异：

| 设备类型 | encode | decode | 说明 |
|---------|--------|--------|------|
| **AD/DA** | `raw = (eng - offset) / coeff` → `writeChannel(ch, raw)` | `readChannel(ch)` → `eng = raw × coeff + offset` | 线性映射，同步读写 |
| **CAN** | `raw = inverseLinearMap(eng)` → `packBits(raw)` → 组装到帧缓冲区 → `sendMessage()` | `receiveMessage()` → 从帧缓冲区 `unpackBits()` → `raw` → `linearMap(raw)` → `eng` | 位打包 + 帧收发。**读操作为异步**：CAN 消息由总线推送，`read()` 返回当前接收队列最新值；`readAndWait()` 带超时等待目标 CAN ID 的消息到达后再解码 |
| **Serial** | `raw = inverseLinearMap(eng)` → `packBits(raw)` → 组装到帧缓冲区 → `writeFrame()` | `readFrame()` → 从帧缓冲区 `unpackBits()` → `raw` → `linearMap(raw)` → `eng` | 整帧收发 + 位打包，与 A429 一致。ASCII 命令按最大长度定义固定帧长序列化。读操作同样异步，`readAndWait()` 带超时等待匹配帧到达 |
| **A429** | 同上 | 同上 | 有 Label 寻址 + 特定编码。读操作为异步轮询接收队列，`readAndWait()` 按 Label 过滤等待 |

### 3.3 HardwareManager（硬件管理器）

**职责**：设备实例生命周期管理，统一读写入口。

```cpp
class HardwareManager : public QObject {
  Q_OBJECT

 public:
  // ── 生命周期 ──
  bool loadFromTopology(const QString& etopoPath);
  bool loadFromDocument(const TopologyDocument& doc);
  void shutdown();

  // ── 统一的读写接口 ──
  // 同步读（返回最近一次采样值；CAN/Serial/A429 可能返回空 QVariant）
  // 失败时抛 DeviceException 或返回空 QVariant（各设备类型实现约定）
  QVariant read(const ResolvedSignal& signal);
  // 带超时的等待读（CAN/Serial/A429：等待目标信号到达后返回工程值）
  // 超时未收到抛 TimeoutException
  QVariant readAndWait(const ResolvedSignal& signal, int timeoutMs);

  // 写操作：失败返回 false，同时发射 deviceError() 信号
  bool write(const ResolvedSignal& signal, double engValue);
  bool writeFrame(const ResolvedSignal& signal,
                  const QByteArray& frameData);

  // ── 设备状态 ──
  DeviceStatus deviceStatus(const QString& deviceId) const;
  QList<QString> onlineDevices() const;

 signals:
  void deviceStatusChanged(const QString& deviceId, DeviceStatus status);
  void deviceError(const QString& deviceId, const QString& message);

 private:
  // deviceId → 驱动实例，一对一
  QMap<QString, IDevicePlugin*> device_pool_;
};
```

**设备匹配逻辑**（从拓扑文档到插件实例）：

```
拓扑 Device → pluginId 字段 → PluginManager::devicesByType()
  ↓
匹配到某个已加载的插件 → pluginAs<T>() 获取 IDevicePlugin*
  ↓
取拓扑 Device.properties 中的配置参数 → device.open(config)
  ↓
存入 device_pool_[deviceId]
```

对于独立引擎，拓扑中预置的 mock 设备也可以直接使用（产线部署时通过替换拓扑文档切换为真实设备）。

**设备清理（shutdown）**：

```
正常关闭 / 用户停止:
  HardwareManager::shutdown()
    → 遍历 device_pool_
    → 逐个 device->close()
    → 清空 device_pool_

崩溃（SEH/signal）:
  CrashHandler 生成 dump → 进程终止
  → OS 回收内核句柄（串口/CAN/文件等）
  → 不尝试调 device->close()（SEH 上下文中调外部驱动不可靠）
```

三种触发路径：

| 触发方式 | 调用链 | 安全 |
|---------|--------|------|
| 用户点 ⏹ 停止 | cancel_flag_ → StepRunner 退出 → QThread::wait() → shutdown() | ✅ |
| 用户关闭窗口 | MainWindow 析构 → HardwareManager 析构 → shutdown() | ✅ |
| 程序崩溃 | CrashHandler → 生成 minidump → 进程终止 | ❌ 不调 shutdown |

### 3.4 StepRunner（指令执行器）

**职责**：测试程序的串行执行引擎。

**取消标志的三种状态**：

```cpp
// cancel_flag_ 的三种状态
enum StepRunnerState {
  RUNNING    = 0,   // 正常运行
  PAUSED     = 1,   // 暂停（等用户操作）
  CANCELLING = 2,   // 停止请求，当前步骤安全点退出后中止
};
```

**单步结果定义**：

```cpp
enum StepStatus {
  PENDING,   // 未执行
  PASS,      // 通过
  FAIL,      // 失败（值不匹配、条件不满足）
  TIMEOUT,   // 超时
  ERROR,     // 设备错误、解析错误等
  SKIPPED    // 因中止/控制流跳过的行
};

struct StepResult {
  int       caseIndex;
  QString   stepPath;       // "0", "1/0/0", "2/THEN/1" 等
  QString   command;        // SET / CHECK / WAIT / LOOP 等
  QString   target;         // UUID hex
  StepStatus status = PENDING;
  QString   message;        // 失败/错误原因
  double    actualValue;    // CHECK/VERIFY 的实际值
  double    expectedValue;  // CHECK/VERIFY 的期望值
  double    tolerance;      // 容差范围
  int       elapsedMs = 0;
  QDateTime timestamp;

  // .etlog 嵌套结构控制流步骤的递归结果
  // 仅 LOOP/WHILE/IF 设置，其余步骤为空
  QList<IterationResult> iterations;  // LOOP/WHILE 的轮次结果
  BranchesResult         branches;    // IF 的分支结果
};
```

**单步执行逻辑**：

```cpp
// stepPath 格式：普通步骤 "0", "1", ...；控制流子步骤 "1/0/0"（第1步/第0轮/第0个子步）, "2/THEN/1"
StepResult StepRunner::executeSingleStep(const TestStepData& step,
                                          int caseIndex,
                                          const QString& stepPath) {
  StepResult result;
  result.stepPath = stepPath;
  result.command = step.command;
  result.timestamp = QDateTime::currentDateTime();

  emit stepStarted(caseIndex, stepPath, step.command, step.target);

  // 检查取消标志
  if (cancel_flag_.load() == CANCELLING) {
    result.status = SKIPPED;
    result.message = QStringLiteral("执行被中止");
    emit stepFinished(caseIndex, stepPath, result);
    return result;
  }

  try {
    // 解析信号
    auto signal = resolver_->resolve(step.target);
    if (!signal.valid) {
      result.status = ERROR;
      result.message = QStringLiteral("信号解析失败: UUID %1 未在 SignalRegistry 中找到").arg(step.target);
      emit stepFinished(caseIndex, stepPath, result);
      return result;
    }

    // 命令分发
    switch (commandType(step.command)) {
      case CommandType::SET:
        result = execSet(step, signal);
        break;
      case CommandType::VERIFY:
        result = execVerify(step, signal);
        break;
      case CommandType::CHECK:
        result = execCheck(step, signal);
        break;
      case CommandType::WAIT:
        result = execWait(step, signal);
        break;
      case CommandType::DELAY:
        result = execDelay(step);
        break;
      case CommandType::LOOP:
        result = execLoop(step, caseIndex, stepPath);
        break;
      case CommandType::WHILE:
        result = execWhile(step, caseIndex, stepPath);
        break;
      case CommandType::IF:
        result = execIf(step, caseIndex, stepPath);
        break;
      // ... 其余命令
    }
  } catch (const TimeoutException& e) {
    result.status = TIMEOUT;
    result.message = e.what();
  } catch (const DeviceException& e) {
    result.status = ERROR;
    result.message = QStringLiteral("设备错误: %1").arg(e.what());
  }

  emit stepFinished(caseIndex, stepPath, result);
  return result;
}
```

**控制流命令的子步骤执行**（LOOP/WHILE/IF 需递归）。LOOP/WHILE 必须收集子步骤结果以判定整体状态：

```cpp
StepResult StepRunner::execLoop(const TestStepData& step,
                                 int caseIndex, const QString& stepPath) {
  int failCount = 0;
  for (int i = 0; i < step.loopCount; i++) {
    for (int si = 0; si < step.subSteps.size(); si++) {
      QString subPath = QStringLiteral("%1/%2/%3").arg(stepPath).arg(i).arg(si);
      auto subResult = executeSingleStep(step.subSteps[si], caseIndex, subPath);
      if (subResult.status != PASS) failCount++;
      if (cancel_flag_.load() == CANCELLING) break;
    }
    if (cancel_flag_.load() == CANCELLING) break;
  }
  // 传播子步骤失败：有失败则 LOOP 整体 FAIL，否则 PASS
  if (failCount > 0) {
    return StepResult{}.setStatus(FAIL)
        .setMessage(QStringLiteral("LOOP 执行完成，%1 个子步骤失败").arg(failCount));
  }
  return StepResult{}.setStatus(PASS);
}
```

**StepPath 索引规则**：

| 场景 | stepPath | 说明 |
|------|---------|------|
| 顶层第 0 步 | `"0"` | 用例内索引 |
| LOOP 第 1 步，第 2 轮迭代，第 3 个子步 | `"1/2/3"` | `父步路径/轮次/子步索引` |
| IF 第 2 步，THEN 分支第 1 个子步 | `"2/THEN/1"` | `父步路径/分支名/子步索引` |
| IF 第 2 步，ELSE 分支第 0 个子步 | `"2/ELSE/0"` | 同上 |
| WHILE 第 3 步，第 1 轮迭代第 2 个子步 | `"3/1/2"` | WHILE/LOOP 使用索引轮次 |
```

**IF/WHILE 条件表达式格式**：

条件字段统一使用字符串表达式，格式为 `<信号标识> <运算符> <值>`，其中：
- `<信号标识>`：步骤 target 列的 UUID（与 SET/CHECK 一致），引擎通过 SignalResolver 解析
- `<运算符>`：`>`、`>=`、`<`、`<=`、`==`、`!=`
- `<值>`：工程值（含单位后缀时先校验单位兼容性）

示例：`7a3f1c... > 100`、`4b2d1a... == 5.0`
引擎在执行 IF/WHILE 时调用 SignalCodec 将表达式中 `<值>` 与当前采样工程值比较。

**超时机制**：

引擎不定义自己的超时，每步的超时直接来自步骤数据 `step.timeoutMs`（kColTimeout 列）。
WAIT 类命令用它做条件等待的上限，硬件阻塞操作也用它做看门狗。
步骤未设超时（`timeoutMs = 0`）时引擎给一个全局默认值兜底（如 30s）。

```cpp
// 从步骤数据读取超时
int effectiveTimeout = (step.timeoutMs > 0) ? step.timeoutMs : kDefaultTimeoutMs;

// 工作线程必须启动事件循环（QThread::exec()），
// 用成员变量 QTimer* 挂在 this 上确保存活
abort_current_op_ = false;
QTimer* timeoutTimer = new QTimer(this);
timeoutTimer->setSingleShot(true);
timeoutTimer->setInterval(effectiveTimeout);

connect(timeoutTimer, &QTimer::timeout, this, [this]() {
  abort_current_op_ = true;
});
timeoutTimer->start();

// 每次硬件操作检查
if (abort_current_op_) throw TimeoutException("操作超时");

// 操作完成后停止定时器
timeoutTimer->stop();
```

**有效超时计算**：步骤 `timeoutMs` 为 0 时使用 `kDefaultTimeoutMs`（30s）。
`abort_current_op_` 为 `std::atomic<bool>`，由超时定时器置 true，被工作线程在每次硬件操作前检查。
每次新步骤开始时先重置为 false 再启动定时器。**不依赖栈分配 QTimer**——栈 QTimer 无事件循环支持时永不触发。`abort_current_op_` 同时响应⏹停止（StepRunner 将 cancel_flag_ 置为 CANCELLING 后一并设 abort_current_op_ = true）。

## 4. ICD 集成路径

### 4.0 ICD Repository 获取方式

ICD 数据源支持三种格式（详见 `icd_utility` 文档）：

| 格式 | 说明 | 加载方式 |
|------|------|---------|
| `.eproto` | JSON 单文件，整个 Repository 一个文件 | `icd::Loader::init(filepath)` |
| `.eprotox` | XML 单文件，同上 | `icd::Loader::init(filepath)` |
| `ICDConfig.xml` / `.json` + 单帧文件 | 多文件配置，一个索引文件引用多个帧文件 | `icd::Loader::init(config_path)` |

两种运行形态下的获取方式：

- **IDE 模式**：ProtocolManager 已通过协议编辑器加载了 ICD Repository，引擎构造函数接收 `icd::Repository*` 直接使用，不自行加载
- **独立引擎模式**：引擎通过 `--icd` 参数接收 .eproto 或 ICDConfig.xml 路径，启动时自行调用 `icd::Loader` 加载：`TestExecutionEngine::loadIcd(path)`

### 4.1 信号选择阶段（设计时，已有）

测试程序编辑器中，通过 `ISignalSelection` 接口弹出四层选择对话框（设备→端口→帧→节点树），选中信号后生成 UUID 写入步骤的 target 列。这部分在 UUID V1.1 中已完成。

### 4.2 信号解析阶段（执行时）

```
UUID → SignalRegistry → deviceId + portName + frameName + nodePath
     → ICD Repository → 节点的 value_type / offset / bit_offset / bit_width
     → SignalCodec 的 coeff / offset 等参数由节点的属性推导
```

### 4.3 编码/解码阶段（执行时）

```
SET 工程值 → codec.encode() → raw / frameBytes → hardware.write()
CHECK → hardware.read() → raw / frameBytes → codec.decode() → 工程值
```

| 🚫 阻断 | ICD Repository 已加载 | `icd_repository_ != nullptr` | 错误: ICD 协议未加载，请先打开项目 |

### 错误处理

| 错误类型 | 表现 | 后续行为 |
|---------|------|---------|
| 前提不满足（未加载拓扑等） | QMessageBox 弹框提示 | 取消执行 |
| 步骤硬件操作失败 | 状态标记 ERROR，日志输出错误详情 | 继续执行下一行 |
| 步骤超时 | 标记 TIMEOUT，日志输出"超时 n ms" | 继续执行下一行 |
| Worker 线程崩溃 | `engineError` 信号 → QMessageBox 警告 | 停止引擎，释放资源 |
| 设备离线 | `deviceError` 信号 → 状态栏图标变红 | 标记当前行 ERROR，继续执行 |
| 用户手动停止 | 当前步骤停止后中断 | 后续步骤标记 SKIPPED |

| | ▶ 运行用例 | 只执行当前用例（右键 Case tab → "运行此用例"） |
| 统计 | PASS/FAIL/TIMEOUT | 只读显示，执行中实时更新 |

### 三种操作入口的关系

| 入口 | 适用场景 | 优势 |
|------|---------|------|
| **Ribbon "运行" 页** | 任何时候 | 按钮大、功能全，发现性最好 |
| **编辑器 ControlBar** | 正在编辑测试程序时 | 一步直达，不用切 Ribbon 分类页 |
| **Sidebar "运行" 页** | 执行过程中 | 专注监控，不占中央区域 |

三处通过共享的 `QAction` 实例保证状态同步——Ribbon 暂停 → ControlBar 的暂停图标也同步变灰。

## 6. 独立引擎（test-executor / test-executor-cli）

独立引擎有两个独立可执行文件，GUI 版与 topology-editor 等一致，CLI 版无任何 GUI 依赖：

| 可执行文件 | 类型 | 依赖 | 体积 |
|-----------|------|------|------|
| `test-executor.exe` | GUI（窗口+树+日志+统计） | etest_engine + etest_ui + Qt5::Widgets | 较大 |
| `test-executor-cli.exe` | CLI（控制台输出，无窗口） | etest_engine + etest_core + spdlog | 轻量，仅几百 KB |

两者共享同一套 `etest_engine` 核心。引擎只管发射信号，GUI 和控制台都是信号的消费者：

```
                    etest_engine (核心)
                          |
                    stepStarted/stepFinished/...
                          |
              ┌──────────┴──────────┐
              ▼                     ▼
     test-executor          test-executor-cli
     GUI QTreeView         控制台 stdout
     树+日志+统计          逐行 PASS/FAIL
     (Qt5::Widgets)        (仅 Qt5::Core + spdlog)
```

### test-executor（GUI 版）

```
test-executor --topology test.etopo --icd icd/config.eproto --program test.etprog
```

| 参数 | 说明 |
|------|------|
| `--topology` | 拓扑文件路径 (.etopo) |
| `--icd` | ICD 数据路径 (.eproto / ICDConfig.xml) |
| `--program` | 测试程序文件路径 (.etprog) |
| `--verify-only` | 仅运行前检查，不实际执行 |

参数可在 GUI 中通过菜单打开。

### test-executor-cli（CLI 版）

CLI 版不链接 `etest_topology` 和 `etest_program`，.etopo 和 .etprog 由 CLI 自身通过 QJsonDocument 提取所需字段后通过 API 传入 engine：

```
test-executor-cli:
  1. QJsonDocument 解析 .etopo
     -> 提取 devices[].id / name / pluginId / properties / ports[].name / portConfig
     -> 用 pluginId 匹配 PluginManager::devicesByType() 找到对应驱动
     -> engine_->setDevices(devices)
  2. icd::Loader 加载 .eproto
     -> engine_->setIcdRepository(repo)
  3. QJsonDocument 解析 .etprog
     -> 提取 TestProgramData 结构
     -> engine_->setProgram(program)
```

```
test-executor-cli --topology test.etopo --icd icd/config.eproto --program test.etprog
test-executor-cli --verify-only --topology test.etopo --icd icd/config.eproto
```

| 参数 | 说明 |
|------|------|
| `--topology` | 拓扑文件路径 (.etopo) |
| `--icd` | ICD 数据路径 (.eproto / ICDConfig.xml) |
| `--program` | 测试程序文件路径 (.etprog) |
| `-o, --output` | .etlog 输出路径（默认 `reports/<程序名>.etlog`） |
| `--timeout` | 全局步骤超时秒数，默认 30 |
| `--verify-only` | 仅运行前检查，不实际执行 |

**stdout 输出格式**：

```
[SUITE] 发动机控制测试套件
  [CASE 0/2] 燃油阀门控制
    [0] SET 燃油阀门开度 = 80% → PASS (12ms)
    [1] CHECK 温度1 > 100°C → FAIL (150ms) | 实际值: 95.3°C
    [1/0/0] SET 子阀门 = 50% → PASS (8ms)
  [CASE 0/2] → FAIL (PASS: 1, FAIL: 1)
[SUITE] → 完成 (PASS: 12, FAIL: 2, TIMEOUT: 1) 耗时 45.2s
```

**退出码含义**：

| 退出码 | 含义 |
|--------|------|
| 0 | 全部 PASS |
| 1 | 存在 FAIL 或 TIMEOUT |
| 2 | 引擎内部错误（崩溃 / ICD 加载失败等） |
| 3 | 参数错误或运行前提检查未通过 |

### UI 布局

## 8. 文件结构

### 分层原则

`etest_engine` 是纯核心库，**不依赖 Qt Widgets**（仅 Qt5::Core），无 GUI 即可独立编译和链接。
GUI 组件建立在引擎之上：

```
etest_engine (无 UI 依赖, 仅 Qt5::Core + spdlog)
  ↑
  ├── etest_core (SignalRegistry, PluginManager)
  ├── icd_utility (ICD Repository)
  ├── etest_app (IDE: ExecutionControlBar / ExecutionMonitorPanel → Qt5::Widgets)
  ├── tools/test-executor (独立引擎: 完整 GUI → Qt5::Widgets)
  └── 第三方程序或脚本
```

引擎核心依赖关系：`etest_engine → etest_core + icd_utility + spdlog + Qt5::Core`，不引入 Qt5::Widgets。

```

## 10. 与现有模块的接口汇总

| 现有模块 | 引擎需要什么 | 提供方式 |
|---------|------------|---------|
| `etest::core::SignalRegistry` | resolve(uuid) → 设备/端口/帧/节点路径 | 引擎构造函数注入指针 |
| `icd::Repository` | find(frameName) → 帧定义 → 节点的编码属性 | 引擎构造函数注入指针 |
| `PluginManager` | devicesByType() → 插件实例列表 | 全局单例，引擎内部直接访问 |
| `IDevicePlugin` | open/close + 设备类型特定的读写接口 | HardwareManager 通过 pluginAs<T>() 获取 |
| `TopologyDocument` | devices[] → 设备列表 + properties → 配置参数 | 引擎构造函数接收 TopologyDocument |
| `TestProgramData` | cases[] → steps[] → 命令和数据 | `StepRunner::executeProgram(program)` |
