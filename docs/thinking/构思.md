## 测试流程描述

在一台定制的工控计算机上，使用这些硬件接口：
- PCI
- cPCI/PXI
- USB
- LAN
- PCIe
- 串口
接入 AD、DA、IO、RS232/422/485、CAN/LIN/Flexray、1553B、A429、VISA SCPI程控设备，通过这个测试平台提供的插件接口，使用这些硬件设备厂商提供的API(或SDK)编写硬件插件。
测试平台运行起来之后，加载所有的硬件设备插件。使用插件实现的自测试接口完成自测试，判断设备是否正常工作。
测试平台加载所有硬件插件并且完成自测试之后，界面上通过树形结构的方式展示所有的硬件列表。
- 树的一级节点（根节点之下的直接孩子）显示厂家
- 二级节点（厂家之下的直接节点）显示分类的节点（如AD、DA、UART、CAN等）
- 分类节点下的节点用于显示具体的硬件。
- 并且显示硬件的连接状态、自检状态、错误状态等信息。

平台提供了可视化设计工具，包括硬件连接拓扑编辑器和帧协议编辑器。
- 硬件连接拓扑编辑器能够让用户通过拖拽连线的方式描述出硬件设备与被测设备（被测设备通常是一个抽象的表示，它对外暴露了各种各样的通讯硬件接口（通道）、测试接口（通道））连接关系。
- 帧协议编辑器用于定义协议的字段的起始比特位、大小端、字段长度、编码方式等信息。

通常，使用这个平台的用户需要测试的内容是一些有实际含义的工程值的描述，例如：
- 对AD采集来说，物理硬件采集的本身是电压、电流，但是工程应用中可以是温度、转速、湿度等等。
- 对DA输出来说，它输出的是电压或是电流，但在工程应用中电压、电流代表的可能是压力、转速、强度等等。
- 对RS232/422/485来说，它是通信类，那么它就需要对串口定义协议，定义单次传输的数据包的格式（也就是帧格式），然后对帧各字段赋予不同的含义，继而表达工程应用中的实际物理量或者信号。
- 对于CAN、A429等来说，它们有相对固定的帧格式，但也需要和RS232一样，需要对帧中的字段赋予工程值含义。

平台提供ICD（Interface Control Document） 数据映射层,它提供以下的能力:
- 假设我们把单独的一个“工程值”叫做一个“信号”
- 实现“工程值（信号）”（如：温度）与“比特流”（如：CAN 报文位偏移）之间的双向转换逻辑
- 负责描述数据的消息格式、字段定义、单位、有效范围。有了这个ICD层之后，就可以把工程“信号”和某一个硬件设备的通道关系起来，也可以和某个通讯协议中的某个数据帧关联起来，也可以和某个通讯协议数据帧中的某些字段关联起来。

有了上述的模块之后，使用这个平台的用户就可以通过编制一定格式的测试用例，使用人能够听懂的话来编制测试流程。例如：
```txt
测试用例：ABCD // 标记测试用开始
步骤1开始 // 标记测试步骤开始
设置压力为5Kpa              // 可能是A429卡的某个通道发送了label为11的帧
判断压力是否为5Kpa，允差±0.5  // 可能是A429卡的另一个通道读取到了label为11的帧
设置空速为5马赫             // 可能是串口卡通道9发送了某种数据帧
判断空速是否为5马赫，允差±0.1 // 可能是AD采集卡某个通道采集了某个通道的电压值，然后转换为了空速
步骤1结束 //标记测试步骤结束
步骤2开始 //标记测试步骤开始
打开驱动电机  // 可能是IO继电器卡的某个通道的开关打开了
读取电机工作状态 // 可能是通过另外的IO采集卡的某个通道获取被测设备上报的工作状态
判断驱动点击是否工作 // 通过设置的值与读取的值进行比较，相等则本步骤通过
步骤2结束 // 标识步骤结束
测试用例结束 // 标识测试用例结束
```

测试平台可以把上边的测试用例转换为脚本（可以基于python、Lua、Javascript）。不管是自然语言描述的测试用例，还是基于 json 格式的测试用例，平台都能将其转化为 编程语言的脚本(下边以lua脚本为例)：
```lua
print("=== 开始执行测试用例：测试用例1 ===")
print("描述：演示测试用例的用法")
print("前置条件：系统正常运行")

-- 指令：ACTION - 用户确认
UserAction("请观察XXX是否是XXXX")

-- 指令：PHOTO - 拍照
TakePhoto()

-- 指令：RECORD - 开始录像
SetRecord(true)

-- 指令：DELAY - 延时5000ms
Delay(5000)

-- 指令：RECORD - 停止录像
SetRecord(false)

-- 指令：SET - 设置温度传感器 37.5
SetDevice("温度传感器", 37.5)

-- 指令：VERIFY - 校验温度传感器
VerifyDevice("温度传感器", 37.5, -0.1, 0.1)

-- 指令：DELAY 1000ms
Delay(1000)

-- 指令：DELAY 2s → 自动转 2000ms
Delay(2000)

-- ===================== 测试用例2 =====================
print("=== 开始执行测试用例：测试用例2 ===")
print("描述：测试可选字段")

-- 指令：ACTION
UserAction("")

-- 指令：SET - 设置湿度传感器 50.0
SetDevice("湿度传感器", 50.0)

print("=== 所有测试用例执行完成 ===")
```
转换过程中，进行语法校验，当出现平台不支持的语法会提示用户的具体的代码位置。

平台提供运行控制界面，用户点击执行按钮，脚本就会开始执行，然后实时的向用户展示执行的步骤，以及每个步骤的设置值和读取值，并记录执行的全过程，在日志窗口输出日志。当用例执行完之后，还可以根据预设值的模板生成测试报告。


## 编程语言选型
- 使用Qt框架来实现跨平台(Windows、Linux、实时操作系统，如QNX/VxWorks)
- 基于Qt的插件机制，实现硬件抽象层（HAL）：
  - 基本接口类封装所有的硬件的基本操作。
  - 再通过一层分类(如AD类、DA类、串口类、VISA类等)的硬件抽象接口统一同类型的硬件接口。将所有接入计算机的硬件通过插件的方式加载和控制
- Python或Lua(Sol2)或者JavaScript(NodeJs嵌入C++)
  - 脚本用于将测试流程转换为脚本代码，脚本可以是 python lua js中的一种

## 其它的一些描述，比较杂乱，还需要整理
- 在硬件层/插件层之上。有一层执行引擎层。这一层需要配合下一层工作
- 在执行引擎层之上，有一层 ICD层，这一层用于解析用户的ICD协议(ICD协议必须支持xml、json)。ICD文件定义了“信号”的详细信息。
- 在ICD层之前有一层测试用例以及测试流程管理层。这一层用户可以通过excel表格或 json文件或yml文件编写测试用例，测试用例中描述的是ICD中定义的信号的处理方式。如设置迎角45°，那么ICD中就定义了迎角是A429协议当label是多少的时候SDI是多少的时候表示迎角。
- 除此之外，应该还有帧协议编辑器，它通过可视化的方式定义通讯协议中的帧的各字段，ICD模块通过某种关系和帧协议联系起来
- 还有硬件连接拓扑图设计，这个打算用Qt的GraphicsView框架实现。
- 测试引擎打算使用Python/Lua/JavaScript中的一种，嵌入到C++代码中运行，测试引擎将测试用例对应的测试流程完全换成脚本代码，C++端封装的对硬件设备的控制，脚本端可以直接调用，以实现测试流程的分支/循环/跳转
- 测试引擎还需要支持变量监视，断点，单步等。
- 测试引擎还需要记录测试流程中的数据，当测试执行完以后，能够将记录的数据生成测试报表
- 硬件设备管理层还需要支持模拟的硬件，以便在开发的时候能够模拟测试/仿真测试
- 尽量以数据驱动，接口驱动，以达到前后端分离，虽然现在用的Qt，但是后续可以迁移到web后端，这样就可以做到云端化、web化
- 插件的“隔离与保护”机制
  - 考虑多进程插件架构
  - 核心引擎是一个进程，每个硬件驱动插件（或者一类硬件）运行在独立的“驱动代理”进程中。
- HAL层读取到的数据考虑引入“数据池”，永远保存最新值。
- 容错与“故障注入” (Fault Injection)：
  - 在 ICD 或协议编辑器层增加故障注入功能
  - 允许用户在脚本中模拟硬件故障。例如：模拟 CAN 报文丢包、模拟 A429 校验错误、模拟某个 AD 通道超出量程。
- 脚本引擎的“影子运行”模式
  - 增加一个 “Dry Run” (空跑/影子) 模式
  - 在这个模式下，所有的硬件插件自动切换到虚拟/仿真状态，执行引擎按照脚本跑一遍逻辑，并检查 ICD 定义的信号边界。
- 帧编辑器与 ICD 的反向生成
  - 帧编辑器不应只是一个展示工具，它应该支持 “所见即所得”的反向同步
  - 用户在帧编辑器里改了一个位域定义，关联的 ICD 信号应自动感知并同步更新。建议引入 UUID 机制 标记信号，而不是依靠名称字符串，防止改名导致引用失效。
- 设计的时候可以考虑先实现`MVP(最小可行性产品)`和核心骨架
