# 硬件产品分析方法指南

> 在 `enpht/` 中拿到一套新的硬件产品文档后，按此流程分析并写入 `docs/thinking/使用场景分析.md`。
> 本指南是对 AD、DA、串口、ARINC 429、CAN、1553B、FlexRay、IO、1394B 共 9 类产品实际分析过程的总结。

---

## 1. 分析前准备

### 1.1 需要什么材料

在 `enpht/<设备类型>/extracted/` 下通常有两个文件（或文件名中包含的章节）：

| 文件类型 | 用途 | 提取重点 |
|---|---|---|
| **用户手册** (`*_user.txt`) | 了解产品的**硬件规格、功能描述、应用场景** | 通道数、速率、模式、耦合方式、工作环境 |
| **API 参考手册** (`*_api.txt`) | 了解**编程接口、数据结构、函数列表、调用流程** | 函数名、参数、数据结构、返回值、程序范例 |

### 1.2 目录惯例

```
enpht/<设备类型>/extracted/   ← 放原始文档（不修改）
docs/thinking/使用场景分析.md  ← 分析结果写入这里（按设备大类追加章节）
```

## 2. 标准分析流程（5 步）

### Step 1：扫描目录

```
1. 用 Read 工具列出 extracted/ 目录
2. 确认有几款产品、几个文件
3. 如果有多款产品（如 IO 类有 4 款），先整理产品线矩阵
```

### Step 2：读用户手册 → 提取核心规格

```
对每款产品提取以下内容：
- 通道数（单端/差分）
- 速率/采样率/波特率
- 量程/输出范围/电压等级
- 工作模式（如 BC/RT/BM、CC/RN/BM）
- 特殊功能（滤波、中断、FIFO、触发、错误注入）
- 电气隔离/耦合方式
```

整理成**产品线矩阵表格**。

### Step 3：读 API 手册 → 提取关键 API

```
- API 前缀（如 EphSerial_、Eph6273_、Eph1394_）
- 连接函数（AutoConnectToFirst / AutoConnectToBusSlot / Open）
- 核心收发函数（Transmit / Receive / SendMsg / GetMsg）
- 配置函数（Init / SetMode / SetCh / SetBitRates）
- 特殊能力函数（FIFO、中断注册、错误注入、过滤）
- 数据结构（帧格式、通道配置结构体）
```

提取出**通用编程流程**（连接→配置→启动→收发→关闭）。

### Step 4：设计 6 个使用场景

每个场景必须包含：

```
1. 用户情景（不超过 5 句话）
2. 物理量与帧格式（具体数值、编码方式、校验规则）
3. 硬件接线示意（如有）
4. 完整 API 调用序列（可编译风格的伪代码）
5. 关键参数表格（说明每个参数的含义和取值范围）
6. 对比/速查类说明（FIFO vs 存储器、中断 vs 轮询等）
```

### Step 5：写入文档

```
打开 docs/thinking/使用场景分析.md
定位到文件末尾
用 ## <设备名称> 作为新章节标题
依次写入：是什么 → 干什么 → 产品线矩阵 → 场景一到六 → API 编程注意事项
```

## 3. 场景设计的 3 条原则

### 原则 1：必须有物理量

不要只说"发送数据"，要说具体的物理意义：

| ❌ 不好的写法 | ✅ 好的写法 |
|---|---|
| "发送转速数据" | "反馈当前发动机转速 4500RPM，编码为 2 字节 (0x1194)，LSB=1RPM" |
| "发送角度指令" | "发送炮塔方位角 135.00°，编码为 2 字节 (0x1A5C)，LSB=0.01°" |
| "接收温度数据" | "接收 PT100 温度 200.0°C，Modbus RTU 协议，0.1°C/bit，原始值 0x07D0" |

### 原则 2：必须有帧格式

每个字节/每 bit 的含义必须说清楚：

```
发送帧（PC → 伺服驱动器 8 字节）：
┌──────┬──────┬──────────┬──────────┬──────┬──────┬──────┬──────┐
│ 0xAA │ CMD  │ DATA_H  │ DATA_L  │ CHK  │ 0x55 │
│ 帧头  │ 命令码│ 数据高位  │ 数据低位  │ 累加和│ 帧尾  │
└──────┴──────┴──────────┴──────────┴──────┴──────┘
```

对于标准协议（NMEA、Modbus、ARINC 429 Label），可以直接引用协议规范。

### 原则 3：必须有真实 API

使用恩菲特实际的函数名、参数类型、数据结构：

```c
// ✅ 正确：使用真实 API
EphSerial_SetCh(cardnum, 0, 115200, 0, 0, 1);
EphSerial_TransmitFIFOBlock(cardnum, 0, 8, txBuf);

// ❌ 错误：使用虚构 API
SerialPort_Config(baud=115200);
SerialPort_Send(data);
```

## 4. 6 个场景的覆盖逻辑

每个设备产品线的 6 个场景按以下逻辑覆盖：

| 场景 | 覆盖维度 | 说明 |
|---|---|---|
| **场景一** | **最基本操作** | 该设备最常见的用法（如 AD 连续采样、DA 静态输出、串口标准收发） |
| **场景二** | **最独特能力** | 该设备区别于其他设备的独特能力（如 AD 触发采样、DA 波形发生器、串口 RS-485 轮询） |
| **场景三** | **先进能力** | 高性能/高效率用法（如 FIFO 流式、硬件过滤、验收滤波） |
| **场景四** | **中断/实时** | 事件驱动/实时响应用法（中断回调、故障即时告警） |
| **场景五** | **多通道/批量** | 大规模通道处理（96 通道采集、32 RT 仿真、64 路 PWM） |
| **场景六** | **故障/同步/组合** | 错误注入、多卡同步、复合卡协同（AD+DA+DIO 一体、PXI 触发、冗余切换） |

这 6 个场景中：
- **场景一 和 场景二** 覆盖了该设备 80% 的日常使用需求
- **场景四 和 场景六** 覆盖了该设备最值得强调的独特硬件能力

## 5. 每种文档的写作模板

### 5.1 产品线矩阵表格

```
| 型号 | 通道 | 速率 | 量程 | 特色 | 适用场景 |
|---|---|---|---|---|---|
| ...  | ...  | ...  | ...  | ...  | ...      |
```

行按产品型号排列，列按"通道→速率→量程/范围→特色功能→适用场景"顺序。

### 5.2 场景写作模板

```
### 场景X：<场景标题>

#### 用户情景

<1-4 句话描述谁在什么测试场景下用>

#### 帧格式定义 / 物理量编码

<表格或 ASCII 帧格式图>

#### API 调用序列

```c
<完整代码，含注释>
```

#### <补充内容>

<参数表 / 对比表 / 时序图 / 注意事项>
```

### 5.3 API 编程注意事项总结

从以下常见维度检查，列出每个产品的特殊注意事项：

```
1. 连接方式（AutoConnect vs Open）
2. 通道号/节点号约束
3. 模式转换步骤（如 CAN 需先 CONFIG 再 NORMAL）
4. 单位/分辨率（如 PWM 10μs/bit）
5. 中断注册/注销配对
6. 收发函数的限制（最多帧数/缓冲深度）
7. 各产品间不兼容的 API 命名差异
8. 多卡/多通道的特殊处理
```
