## 资料整理

### 一、IATP_设计方案.md 要点

**六层架构**：应用层 → 用例管理层 → 测试引擎层 → ICD信号层 → 硬件抽象层(HAL)

**HAL层插件接口体系**（src/core/plugin/）：
- `IPlugin` — 插件根接口，定义生命周期(initialize/start/stop/uninitialize)和元数据
- `IDevicePlugin` — 设备插件基类，加设备生命周期(openDevice/closeDevice)、状态、自检、simulate
- 类型特化接口：IADevicePlugin(v3.0)、IDADevicePlugin(v1.0)、ICANPlugin(v1.0)、IArinc429Plugin(v1.0)、ISerialDevicePlugin(v1.0)、IDioPlugin、IPulsePlugin、IMil1553Plugin、IVisaPlugin（部分接口尚未实现或不存在）

**ICD信号层**：5个子模块 — SignalMapper(UUID→通道映射)、ProtocolRegistry(协议定义仓库)、FaultManager(故障注入)、SignalValueCache(CVT)、DataPool(Pub/Sub)

**用例管理层**：JSON中间格式(10基本指令+3控制流指令)，格式转换(Excel/YML→JSON→Lua)

**测试引擎层**：Lua 5.4 + sol2，Lua Debug Library 实现断点/单步/变量监视

**技术栈**：Qt 5.12.12 / C++17 / CMake+Ninja / QPluginLoader

**已知不足**（用户自述"这个设计我觉得并不好"）：
- ICD层设计过于抽象，ProtocolRegistry缺少细粒度定义
- 部分设备接口覆盖不全（DA/DIO/1553B/FlexRay/1394B等）
- 整体架构可能过于复杂

### 三、eph435 C# 项目关键设计

**项目结构**（7个工程）：
```
EphAutoTest.sln (.NET 4.7.2, DevExpress V24.2)
├── EphAutoTest                — 主WinForms应用
├── EphAutoTest.Infrastructure — 基础设施（枚举、序列化）
├── EphAutoTest.ICD            — ICD协议管理层
├── EphAutoTest.IO.Inf         — IO接口层（IIoSession/IIoOperation/IIoManager）
├── EphAutoTest.IO.Imp         — IO设备实现层（~30种设备会话）
├── HAutoTest.IO(EphAutoTest.IO) — 遗留WCF服务层
└── IcdExpress                 — 独立ICD查看/调试器
```

**关键设计模式**：

**1. URI设备工厂（IoManager）**：
```csharp
// 路径：EphAutoTest.IO.Imp\IoManager.cs
public class IoManager : IIoManager {
    public static readonly IoManager Instance = new IoManager();
    public IIoSession Create(string uri) {
        // 按URI子串匹配设备类型：E1394::EPH5277::PXI3::13
        if (uri.ToUpper().Contains("5410")) return new Eph5410Session();
        else if (uri.ToUpper().Contains("5272")) return new Eph5272ChannelSession();
        // ... ~30种
    }
}
```

**2. 设备会话层次（IIoSession → IoBaseSession → IoCustomSession → 具体设备）**：
- `IIoSession`：Open/Close/Start/Stop + IsSimulate + 事件
- `IIoOperation`：Read(string path) / Write<T>(string path, T value)
- `IoCustomSession`：桥接ICD，Read/Write通过路径查IcdNode

**3. ICD XML Schema 细粒度定义**：
- `IcdConfig.xml` 索引所有帧定义文件
- 每个帧一个XML文件，含 `ICDData → Item → Childs` 递归字段分解
- 字段属性：Offset/StartBit/BitWidth/Type/Name/Tag(语义标签)
- 缩放：IsScaled/ScaleA/ScaleB
- 校验和类型：Sum/XOR/Count/Head/Length（通过Tag标记）
- 帧类型：iftData(接收)/iftCmd(发送)/ifConfig(配置)

**4. 信号值类型体系（IIcdValue → IcdValueBase → 具体类型）**：
```
IcdBitValue / IcdBoolValue / IcdByteValue / IcdUShortValue / IcdUIntValue
IcdIntValue / IcdLongValue / IcdULongValue / IcdFloatValue / IcdDoubleValue
IcdStringValue / IcdBytesValue / IcdSumValue / IcdXorValue / IcdHeadValue
```
Template Method模式：Extract(byte*) / UnExtract(byte*) / Convert() / UnConvert()

**5. 事件驱动Engine**：
```csharp
// TestEngine不直接操作硬件，发事件由UI处理
public event Action<TestEngine> WriteSignalRequired;  // SET指令
public event Action<TestEngine> AutoCheckRequired;    // CheckAuto指令
public async Task RunProgAsync(bool stepping) { ... }
```

**6. ANTLR4 DSL测试语法**：
```
Prog ISI-TP-F3421-01-001 {
    Case ISI-TC-F3421-01-001-0010 {
        Desc "电源与输出接口检查";
        Step 1 {
            SET "Ps" 98 "KPa";
            CheckAuto "迎角" 25.0 0.5 1.5;
            ACTION "观察仪表显示是否正常";
        }
    }
}
```
- ANTLR4 词法/语法分析器 → DslGrammarVisitor → ProgramModel(内存模型)
- Excel用例 → 转换器 → DSL文本 → 编译 → 执行

**7. 多产品支持**：
- 信号命名空间化：`ISI-01#A429_IN1(050)` 产品名#信号名
- 测试结果按产品存储在 `CmdModel.ResultMap` 字典中

### 四、IATP vs eph435 核心差异分析

| 维度 | IATP方案（当前） | eph435（已交付） | 差异影响 |
|------|----------------|-----------------|---------|
| 设备路由 | 固定类型接口继承 | URI字符串模式匹配 | eph435更灵活，新增设备只需加字符串匹配 |
| ICD协议定义 | ProtocolRegistry抽象概念 | 细粒度XML Schema + 位级分解 | eph435可直接生产使用，IATP太虚 |
| ICD Schema格式 | 未定义 | XML | IATP需定义格式 |
| 校验和 | CRC/Checksum（未具体） | SUM/XOR/Count/Head多种Tag标记 | eph435方案更完整 |
| 信号值转换 | 线性/多项式/枚举/脚本 | Extract/UnExtract/Convert/UnConvert | 思路一致，eph435有完整实现参考 |
| 用例格式 | JSON中间格式 | ANTLR4 DSL + Excel | 方向差异大 |
| Engine设计 | IICDEngineInterface直接调用 | 事件驱动 | eph435松耦合更优 |
| 桥接模式 | 无 | IoCustomSession + IcdManager.Find(path) | IATP缺少这一层 |
| 多产品 | 未考虑 | 信号命名空间化 | IATP需要补充 |
| HAL职责 | 包含编解码 | 仅原始字节收发 | IATP可以简化 |

## 关键问题对话以及确认后的执行策略

### 第1轮 — 设计方向确认（2026-05-13）

**问题1：最想改的部分是什么？**
→ 回答：ICD信号映射与协议层（太抽象，缺少位级定义、校验和类型等细节）

**问题2：哪些eph435的设计值得沿用？**
→ 回答：① URI设备路由（IoManager.Create(uri)工厂） ② ICD XML Schema细粒度定义 ③ IoCustomSession桥接模式

**问题3：ICD Schema用什么格式？**
→ 回答：同时支持XML和JSON

**问题4：设备路由方式怎么改？**
→ 回答：保留现有接口层次（IPlugin→IDevicePlugin→特化接口）+ 增加URI工厂

**问题5：IoCustomSession桥接怎么实现？**
→ 回答：ICD层做编解码，HAL层只传原始字节

**问题6：URI描述能力的格式？**
→ 回答：capability:type:feature 风格（如 cap:ad:16ch:1msps:14bit）

**问题7：ICD Schema和SignalMapper的边界？**
→ 回答：Schema=帧结构（位布局/校验和），Mapper=信号→帧→通道映射

**问题8：工程值→原始字节的转换模型？**
→ 回答：三阶段模型 — 工程值↔原始值(Mapper) → 原始值↔帧字段(Schema) → 帧字节↔物理发送(HAL)

**确认的设计方向：**
- ICD层：沿用eph435的XML结构+新增JSON，Schema与Mapper分离，三阶段转换
- HAL层：保留接口层次加URI工厂，URI描述能力，只传原始字节不参与编解码
- 桥接：ICD层做编解码，HAL层只收发原始字节
