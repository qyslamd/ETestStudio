# 如何模仿一个 ETest 开发计划

## 一、ETest 核心架构分析

ETest 是凯云科技推出的国产自主可控半实物仿真测试集成开发环境，其核心架构设计值得深入分析。

### 1.1 ETest 技术栈

ETest 采用分层架构设计，从底层到顶层依次为：

- **驱动层**：采用 VISA 虚拟化仪器标准封装所有硬件板卡驱动，确保硬件驱动对上服务的标准化
- **核心层**：包含 ETL 编译器、测试程序执行器 ETestX、守护服务 ETestD
- **开发工具层**：监控界面渲染器、UI 组件库、VSCode 插件、命令行工具
- **应用层**：面向不同行业的测试系统

### 1.2 核心技术特性

ETL（Embedded Test Language）是 ETest 的核心，它是一种嵌入式测试领域专用语言，用于描述测试环境中的设备接口、连接拓扑、通信协议、操作面板和测试脚本。ETL 编写的测试程序可以在 ETL 运行器上直接执行，运行器的核心是异步事件循环架构。

异步事件循环是 ETest 的核心技术特点：测试脚本在主循环上执行，主循环中无任何阻塞操作，所有的 I/O 都被异步执行，在高性能线程池中运行着异步 I/O、复杂的计算模型、数学仿真模型以及远程的驱动代理。

### 1.3 支持的总线类型

ETest 支持多种工业总线：RS232/422/485、1553B、CAN、TCP、UDP、AD、DA、DI、DO、ARINC429、AFDX、RapidIO、I2C、SPI、FC-AE-ASM、USB 等，基本覆盖了工业测试领域的主流接口。

### 2.2 核心模块说明

#### 2.2.1 硬件抽象层设计

硬件抽象层是整个系统的基础，需要为每种总线类型定义统一接口，然后针对不同厂商的板卡实现具体封装。建议采用策略模式设计：通过抽象接口定义统一的行为，不同厂商驱动实现具体逻辑。

对于 1553B 总线，需要支持三种工作模式：BC（总线控制器）、RT（远程终端）、MT（监控终端）。接口应包括发送命令、接收数据、错误注入、时间同步等功能。

对于 ARINC429 总线，需要支持多通道收发、不同波特率配置（12.5K、50K、100K）、Label 过滤、SDI/SSM 解析等功能。

对于 CAN/CAN FD 总线，需要支持标准帧和扩展帧、ID 过滤、波特率配置、发送接收等功能。

对于 FlexRay 总线，需要支持周期帧和事件帧配置、启动帧发送、调度表管理等功能。

对于 AD/DA/IO，需要支持采样率配置、触发设置、量程设置、数字量输入输出控制等功能。

#### 2.2.2 协议管理模块

协议管理模块负责定义和管理各种通信协议。参考 ETest 的设计，建议支持可视化协议编辑功能，用户可以通过图形界面定义协议字段、设置字段属性（自动匹配、自动验证、自动值等）。

协议定义应支持层次化结构，可以描述帧头、数据、校验等部分。每个字段可以设置数据类型、长度、字节序、解析规则等属性。

#### 2.2.3 测试执行引擎

测试执行引擎是核心中的核心，建议参考 ETest 的异步事件循环架构。测试脚本在主循环中执行，主循环中不能有阻塞操作，所有 I/O 都必须是异步的。

引擎应支持多种测试模式：快速测试（无需编程，通过配置完成）、自动化测试（通过脚本批量执行）、测试系统开发（面向不同行业的专业测试系统）。

#### 2.2.4 数据管理模块

数据管理模块负责存储和管理测试数据。应支持实时数据记录、时间戳同步、测试数据分析等功能。建议使用 SQLite 存储结构化数据，二进制文件存储原始波形数据。

### 2.3 开发模式设计

参考 ETest 的四种使用模式：

**快速测试模式**：工程师无需编写测试程序，仅通过可视化配置完成测试环境、信号与协议的设置，然后生成测试页面进行人工操作。

**自动化测试模式**：在快速测试配置的基础上，通过图形化或脚本方式开发测试程序，通过运行测试程序实现自动化测试。

**测试系统开发模式**：在自动化测试的基础上，设计 UI 界面，打包发布独立的测试软件，形成可独立运行的测试应用程序。

**实时仿真模式**：支持 C 程序自建模型，集成 Simulink、同元 MWorks 等仿真工具接口，实现仿真模型开发与运行。

## 三、技术选型建议

### 3.1 Qt 版本选择

建议选择 Qt5.15 LTS 版本或 Qt6。Qt5.15 是目前最稳定的长期支持版本，社区资源丰富，各种第三方库支持完善。Qt6 是最新版本，特性更多，但需要评估第三方库的兼容性。

### 3.2 跨平台策略

跨平台支持是 ETest 的重要特性，参考其设计，建议：

Windows 平台：使用 LoadLibrary 加载 DLL，注意 UTF-8 编码处理。

Linux 平台：使用 dlopen 加载 SO 文件，考虑实时性需求可使用 RT 内核补丁版本。

国产操作系统：麒麟、统信等系统基本兼容 Linux 方案，主要需要测试驱动兼容性。

### 3.3 数据库选择

SQLite 是最合适的选择，轻量级、零配置、跨平台，非常适合嵌入式测试场景。

### 3.4 脚本语言集成

建议支持 Lua 和 Python 两种脚本语言。Lua 轻量级、嵌入方便，适合实时测试脚本；Python 生态丰富，适合复杂的数据处理和自动化分析。

## 四、开发里程碑规划

### 4.1 第一阶段：基础设施（4 周）

完成项目搭建、基础框架设计、驱动管理模块开发、基础接口定义。

核心交付物：DriverManager 类实现，支持动态加载厂商驱动；统一接口基类 IBusInterface 定义；基础通信类实现（串口、网口）。

### 4.2 第二阶段：1553B 总线支持（6 周）

完成 1553B 驱动封装、协议解析、BC/RT/MT 模式支持、错误注入功能。

核心交付物：1553BInterface 类实现；支持三种工作模式切换；命令字/数据字解析器；完整测试用例示例。

### 4.3 第三阶段：ARINC429 总线支持（4 周）

完成 ARINC429 驱动封装、多通道管理、协议解析、Label 过滤功能。

核心交付物：A429Interface 类实现；多通道收发支持；Label/SDI/SSM 解析器；协议配置 UI。

### 4.4 第四阶段：CAN/CAN FD 支持（4 周）

完成 CAN 驱动封装、波特率配置、过滤器设置、帧解析功能。

核心交付物：CanInterface 类实现；标准帧/扩展帧支持；多过滤器配置；CAN FD 兼容性处理。

### 4.5 第五阶段：FlexRay 支持（4 周）

完成 FlexRay 驱动封装、周期调度、启动帧配置功能。

核心交付物：FlexRayInterface 类实现；调度表配置；周期帧/事件帧支持。

### 4.6 第六阶段：AD/DA/IO 支持（4 周）

完成数据采集卡驱动封装、采样配置、触发设置功能。

核心交付物：AdDaInterface 类实现；多通道采样配置；软件/硬件触发支持。

### 4.7 第七阶段：协议模板系统（6 周）

完成可视化协议编辑、协议解析器、协议模板管理功能。

核心交付物：ProtocolTemplate 类设计；可视化协议编辑器；JSON/YAML 模板解析。

### 4.8 第八阶段：测试引擎（6 周）

完成测试执行器、测试用例管理、测试序列执行功能。

核心交付物：TestEngine 类实现；测试序列解析器；结果收集与报告生成。

### 4.9 第九阶段：UI 界面（8 周）

完成完整 GUI 开发、项目管理界面、环境配置界面、监控面板设计器。

核心交付物：完整 Qt 应用程序；项目管理 UI；可视化监控面板；测试报告生成。

### 4.10 第十阶段：集成与优化（4 周）

完成系统集成、性能优化、跨平台测试、文档编写。

核心交付物：可发布版本；用户手册；API 文档。

**预计总开发周期：约 10 个月（一人开发，AI 辅助）**

## 五、关键技术难点与解决方案

### 5.1 实时性保障

30ms 以下的实时性要求是技术难点之一。参考 ETest 的做法，建议：

使用 QThread 的高优先级设置，确保测试线程获得足够的 CPU 时间。

将耗时操作放入独立线程池，避免阻塞主事件循环。

对于高精度需求场景，考虑使用 QDeadlineTimer 替代 QTimer。

### 5.2 多板卡同步

多总线协同工作需要精确的时间同步，建议采用：

IRIG-B 时间码同步（如果板卡支持）。

软件时间戳同步，通过统一的时间基准进行校正。

### 5.3 可扩展性设计

参考 ETest 的 VISA 虚拟化思路，建议：

定义标准的驱动接口规范。

支持插件化的驱动加载机制。

提供 SDK 供第三方扩展。

## 八、总结与建议

开发一个类似 ETest 的测试系统是一个复杂的工程，需要考虑硬件驱动适配、协议解析、实时性保障、跨平台支持等多个方面。建议从以下几个方面入手：

首先，定义清晰的接口规范，确保不同厂商的驱动可以灵活替换；其次，设计高效的测试执行引擎，保证实时性能；再次，提供灵活的可视化配置工具，降低使用门槛；最后，考虑扩展性设计，支持第三方插件集成。

整个开发过程建议采用迭代式开发，先实现核心功能，逐步完善周边功能。同时充分利用 AI 辅助工具提高开发效率。
